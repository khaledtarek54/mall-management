# Atriom — working guide for AI / dev sessions

Egyptian mall-management ERP · Laravel 13 · PHP 8.4 · Filament 4 · MySQL (prod/local) / sqlite `:memory:` (tests).
Operator **Eltizam** runs malls for owners (**Jawad**); **tenants** are the retailers.

**[docs/README.md](docs/README.md) is the index of the whole documentation tree** — read it if you are looking for something and do not know where it lives. **Read [docs/OVERVIEW.md](docs/OVERVIEW.md) first**, then the relevant **[docs/modules/NN-*.md](docs/modules/README.md)** before changing any module's logic — each has *Business rules*, *Extension points (how to change safely)*, and *Gotchas*.

**The tree was consolidated 2026-08-19** from **201 markdown files to 85** (excluding the handbook build source), and it is kept to four questions: *how the system works* (the six docs at `docs/` root) · *how each module works* ([`docs/modules/`](docs/modules/README.md)) · *what is missing* ([`docs/gap-analysis/README.md`](docs/gap-analysis/README.md) — **ONE** document, vs Yardi + the FM specialists + Odoo) · *how to run it* ([`operations/`](docs/operations/), [`qa/`](docs/qa/README.md), [`integrations/`](docs/integrations/), [`api/`](docs/api/MOBILE-API.md)). ## Conventions — do these
- **Tests:** `vendor/bin/pest --parallel` (Pest 4). Keep it green. Add a regression test for every bug fix in `tests/Feature/Regression/`; scenario tests live in `tests/Feature/Scenarios/`.
- **CI auto-runs are PAUSED** (2026-07-29, owner's call — the pipeline is too slow for the push loop). `.github/workflows/ci.yml` fires only on `workflow_dispatch`. So the conformance gates (PropertyIsolation, GlRegistry, MediaPrivacy, AdminSmokeManifest, **DashboardLayout**, PostingDateGuard, VatRateSetting, **ActionAuthz**, **QueueJobSafety**, **ConcurrencyPolicy**, **RecordStateRefresh**, **PhpExtensions**) + PHPStan + Playwright + `composer audit` are **ADVISORY**: nothing blocks a bad change. **Keep `pest --parallel` green locally before every push** — a red push is silent, not a red check.
  - **The jobs themselves were repaired 2026-07-29** and a manual run now actually works: `gh workflow run ci.yml`. All four had been failing on *every* run since ≥2026-07-23 for non-product reasons — `composer audit` missing `--locked` (it audited nothing, ever), PHPStan reading a baseline with **absolute paths** (green on one laptop, red everywhere else), and two timeouts set below the real runtime. Worth a manual run before anything risky.
  - **Cost, measured 2026-08-10: the suite is ~1.5 min** — **795s → 75–97s (~9×)** on the same ~3.68k cases (`pest --parallel`, 10 workers; the spread is background load, so measure on a quiet machine or the numbers lie by 3×). Two independent fixes got it there, and the old note here — ~20 min, blamed on migration replay, with `php artisan schema:dump` as the lever — was **wrong on all three counts**. Migrating 170 migrations into sqlite `:memory:` costs ~1.5s per worker, ~0.3% of the run. The real cost was `RolesPermissionsSeeder`, called from ~230 `beforeEach` blocks (~1,700 test cases) at **925ms a call**: spatie forgets its permission cache on every `saved`, and `Permission::findOrCreate()` reads back through that cache, so building the (then 182-key) catalogue one row at a time reloaded it 182 times. Bulk-inserting the rows and wiring role grants in one pass took it to **11ms** with a byte-identical RBAC end state — verified by diffing both seeders' role→permission dumps (14 roles, 182 permissions, every grant equal), and pinned by `RolesPermissionsSeederBulkWriteTest`. That test warms spatie's cache against an empty catalogue first, because the bulk write's one real hazard is skipping the `saved` hook that would have invalidated it.
  - **The second fix was shape, not speed: Pest parallelises per FILE.** `AllFiltersSweepTest` swept every admin table in ONE 80s case, so it pinned one worker while nine idled and set the floor under the whole suite — no optimisation elsewhere could get below it. It is now sharded across `AdminFilterSweepShard{1..4}Test.php` off shared scaffolding in `Tests\Support\FilterSweep` (a class, not file-scope helpers: a parallel worker only loads the test files it owns, and re-declaring them per shard is a fatal redeclaration). paratest's per-method `--functional` mode would remove the need — but it **crashes** in Pest's `WrapperRunner` (`realpath()` on a `file::method` string), so files are the only unit of parallelism we have. **Sharding costs CPU to buy wall-clock** (each shard re-seeds `DemoSeeder`), which only pays while a file dominates the critical path — past that the binding limit is total CPU ÷ workers, and the answer is to cut work, not split it further.
  - **If the suite slows down again, profile before theorising** — `pest --parallel --log-junit <file>` gives per-case times. Two traps: they are wall-clock under 10-way contention and overstate solo cost by ~5-6× (confirm any suspect file by running it alone), and a run sharing the machine with another suite inflates *everything* ~3.7× uniformly, which reads exactly like a real regression. Known next levers, both measured, neither taken: `DemoSeeder` writes **1,287 activity_log rows** (suppressing them is −21% of its runtime), and it issues **18k queries for 274ms of actual SQL** — the cost is PHP per-query overhead, most visibly ~1,400 repeated `account_mappings` lookups and ~560 `accounting_periods` lookups in the GL posting path, which memoising would speed up in production too.
  - **Suite exits 255 with NO output at all?** That is almost always two test files declaring the same file-scope helper — a fatal redeclaration during collection, before any test runs. It has happened three times (`makeViolation`, `optionOn`, `annualPctLease`). `--parallel` hides it (each worker only loads its own files) and every instinctive recovery — re-run, run the directory, add a `--filter` — loads everything and dies identically. **The one command that works:** `vendor/bin/pest tests/Feature/Scenarios/TestHelperUniquenessConformanceTest.php` — a path-scoped run loads only that path, and the gate names both files. The fix is usually to *reuse* the existing helper, not rename yours; shared ones belong in `tests/Pest.php` or a class under `Tests\Support`.
- **Business logic** goes in single-action services (`app/Services`); keep controllers + Filament pages thin.
- **Docs are part of "done":** changing a module's logic → update its `docs/modules/NN-*.md` (+ `docs/OVERVIEW.md` if cross-cutting) **in the same commit**.
- **Local DB:** MySQL; reseed with `php artisan migrate:fresh --seed` after a feature (`DemoSeeder` = canonical demo data). **`LedgerLearningSeeder` is the THIRD dataset (2026-08-25): a set of books small enough to check in your head** — the empty mall plus FIVE documents (two invoices, a payment, a half-applied credit note, one cost) whose trial balance is seven lines totalling 15,700 each side. It exists because there was nothing between 703 journal entries you can only believe and zero you cannot read. Every entry posts through `LedgerPoster::sync()`, never as hand-written journal rows — a seeder that wrote its own entries would teach a ledger that cannot drift, and drift is most of what module 21 is. The half-applied credit note is the row that earns its place: it credits AR in full on ISSUE and stands until applied, so the tenant ledger says 4,700 and the control account says 3,700 and **both are right** — the reconciling item every accountant meets at their first month-end, which a dataset without one teaches does not exist. `LedgerLearningSeederAddsUpTest` pins every figure, because a docblock stating numbers that nothing checks is how a teaching set drifts into teaching something false — it caught two of my own errors: a credit note debits CONTRA-REVENUE (`sales_returns`) rather than reducing the revenue line, and a trial balance is each account's NET balance, not the sum of every debit line (30,700 of gross movement is not a trial balance). **`LearningSeeder` is the empty-mall variant** — the same reference data `atriom:install` lays down, one property, 12 vacant units, 3 tenants and *nothing else*, so an experiment's own numbers are the only numbers on screen.
- **Commits:** push to `main` directly (owner's established preference). End commit messages with the `Co-Authored-By:` line.

## Invariants — don't break
- **Money / AR:** `Invoice::recomputeTotals()` is the single source of truth — `paid_amount = captured payments + credit_applied_amount + applied tenant credit (`TenantCreditApplication`) + netted security deposit (`DepositApplication`)`, `balance = total − paid_amount`. Never set `paid_amount`/`balance` directly elsewhere. **FOUR channels, and every calculation that decides "how much of this invoice is settled" must count all four** — adding one means also updating `Invoice::capturedCashPaid()` (none of the three non-payment channels is cash, so the void guard must exclude them), the cancel-invoice release (or the settlement strands on an invoice that left the books), and BOTH payment over-allocation guards (`Payment::assertInvoicesNotOverAllocated()` and `refitAllocationsToBalance()` — omitting one lets a payment over-settle an invoice another channel already paid, burying the excess as negative AR; that has happened once already). **Item-level allocation (`invoice_item_payment`, MF-06) is NOT a fifth channel** — it records how an already-counted settlement splits across the lines. `App\Support\InvoiceItemSettlement` derives every per-line figure from `paid_amount`, so the item outstandings always sum back to `balance`; never store a per-item balance, that is a second truth about the same money.
- **An invoice's debtor is DERIVED on the form, and is NOT an invariant of the model.** The invoice form shows `tenant_id` read-only beside the lease picker and `CreateInvoice` re-derives it from the lease on save — a disabled field's value still arrives in the Livewire payload, so trusting it lets a crafted request bill a party who never agreed to the charge (until 2026-08-17 a free tenant picker made that two clicks in the UI). **Do NOT promote this to a model-level equality rule** — that was tried on 2026-08-17 and the full suite refused it, correctly: `IssueInvoiceService::issue()` takes an explicit `$tenantId` so a violation fine, a bounced-cheque fee and a late fee carry the debtor stated on their SOURCE document, and a DRAFT invoice may be freely re-homed to another lease before it is issued. Both are deliberate. The rule holds only on the one path where "the form never states a debtor" is unambiguously true.
- **General ledger:** `LedgerPoster::JOURNALIZERS` is the **single registry** of what posts to the GL; all four dispatch paths (real-time hooks · `accounting:sync-ledger` sweep · close gate · `billing:reconcile` drift check) **derive** from it via `LedgerPoster::sources()` — never re-list them. New money source = one registry line + its `LedgerRealtimeSync::SOURCE_DATE_COLUMNS` entry; `GlRegistryConformanceTest` fails CI otherwise. **A GL test that calls `LedgerPoster::post()`/`sync()` directly proves only the journalizer's arithmetic** — at least one test per source must drive the real service + the sweep and assert the tie-out. (This exact gap let applied SLA penalties cut a vendor bill while posting nothing — see [modules/21](docs/modules/21-general-ledger.md#gl-registry-gate).)
- **Tax** on service charges; **base rent is VAT-exempt in the SHIPPED CATALOGUE — a row, not a rule** (measured 2026-08-23): pointing `base_rent` at a tax code on `/admin/charge-codes` is configuration, needs no deploy, reaches every lease already on the books (since EG-01) and turns **no gate red** — `ChargeCodeVatTreatmentConformanceTest` seeds its own catalogue and never reads the operator's database, so the PHP edit is only for changing what a FRESH INSTALL ships. Law 157/2025 makes that the operator's own configuration act, not a question for us; what is still portfolio-wide is telling two units in ONE mall apart (EG-02 — the per-charge `vat_rate` override is importer-only and moves the rate, not the tax code). **Marketing levy 5%** of base rent (that one IS a lease term, so it stays in settings — and is now actually editable there: it had no screen at all until 2026-08-12, so "configurable" was a claim only a deploy could honour). Two separate questions, two separate homes: **which supplies are taxable** is `charge_codes.tax_code` — the accountant's ruling, a row, no deploy (where Yardi puts it too) — and **what that tax charges** is the `tax_codes` + `tax_rates` catalogue at `/admin/tax-codes`. A rate is a **dated rung**, never a column: `Vat::rateForType($code, $on)` resolves for the DOCUMENT's date, so a rise can be entered in advance and a back-dated invoice keeps the rate that was in force. `TaxSettings::vat_standard_rate` is GONE (2026-08-12) — settings hold policy, master data holds rates. The catalogue is **the operator's own `account.tax` sheet** ([docs/accounting/EGYPTIAN-TAX-CATALOG.md](docs/accounting/EGYPTIAN-TAX-CATALOG.md)): VAT · stamp · schedule · withholding, each in both directions — **never invent a row beyond it, and never drop one** (`TaxCatalogueConformanceTest` gates both). **Stamp + schedule were COMMISSIONED 2026-08-19** and a fresh install ships them on (an existing DB gets the posting role backfilled and stays off — a reseed must never reactivate a code the operator retired). The blocker was never mainly the accounts: all three journalizers threw the document's own `tax_code` away — the invoice one summed every line's tax into one accumulator and credited `vat_payable`, the vendor-bill and expense ones hard-coded `vat_recoverable` — so an active stamp code would have put 20% of a supply on the VAT return, under the VAT liability, balanced and tied out. **Tax now groups by the tax code's own posting role**, exactly as revenue groups by the charge code's, with VAT as the floor for a document naming no code. The asymmetry is the real content and must not be flattened: output stamp/schedule are LIABILITIES, input stamp/schedule are **EXPENSES** (`stamp_tax_expense` / `schedule_tax_expense`), because neither has a credit mechanism the way input VAT does — copying the VAT shape there grows a receivable nobody can ever collect. `TaxCode` still refuses to activate a taxable code with no rate or no posting role, so an incomplete catalogue is inert rather than a trap. Activation grants nothing on its own: a code taxes a supply only when a CHARGE CODE points at it, which is the accountant's ruling and a row. **Every origination point calls `App\Support\Vat::rateForType($code, $on)`** (or `Vat::onType()`); a service calling `standardRate()`/`on()` directly can't see the ruling and fails `ExemptChargeTypesAgreeAcrossPathsTest`, and a literal rate anywhere fails `VatRateSettingTest`. `Vat::EXEMPT_TYPES` + `Vat::DEFAULT_STANDARD_RATE` are the FLOOR for an unseeded catalogue, not the policy — they must resolve identically to the seeded catalogue (`ChargeCodeVatTreatmentConformanceTest`), exactly as `InvoiceJournalizer::REVENUE_ROLE` floors the posting roles. Only **origination** reads any of it: an issued invoice keeps the rate it was billed at, so neither a rate change nor a treatment change ever rewrites history. **For a recurring charge, origination is BILLING, not the day the schedule row was written** — `charges.vat_rate` is an OVERRIDE and null is the normal state, with `Charge::resolvedVatRate($on)` the one place that answers what it bills on a date. Storing the catalogue's answer on the row is what broke this until 2026-08-12: the rate froze for the life of the lease, so a rise entered in advance reached every one-off charge and **never reached rent or service charge** — most of the money — and the amendment path carried the stale rate onto the new row too. Proven, not argued: with a rise to 20% effective 1 Sept, the resolver answered 20 for a September document while the September invoice billed 14. **`charges.vat_applicable` is an override on exactly the same terms, and that was the half nobody fixed until 2026-08-22 (EG-01)** — left `boolean default(true)` NOT NULL and written by thirteen services from `Vat::rateForType($type) > 0`, which is the WORSE half because `resolvedVatRate()` tests it FIRST and returns before the catalogue is consulted. A `base_rent` row is born `false` (rent is in `EXEMPT_TYPES`) and can never become taxable again: measured, with the charge code pointed at `VAT_14` the resolver answered 14.0, the charge resolved 0.0, the billing run raised a rent line with 0.00 VAT where 14,000 was due — and a rate the operator had deliberately TYPED was discarded too, because the short-circuit runs before the rate is read. Law 157/2025 makes that the exact change this operator is about to attempt. Now **nullable with null the normal state**, every row backfilled, and the test is `=== false` not falsy. **No screen ever offered it as a tick** — all three UI/import sites derived it — so nothing was preserved that anyone had stated; the operator's channel is the rate they type, and `vat_rate = 0` still holds a supply untaxed. An explicit `false` keeps its meaning and still wins over both. **Never copy the flag through a `(bool)` cast** — that turns null into false and re-freezes the row, which is what `TransferUnitOwnershipService` did to every resale. (`TaxabilityIsNotFrozenOntoAChargeRowTest`, `VatRiseReachesRecurringRentTest`.) **A document line records WHICH tax it carried** (`invoice_items.tax_code`, defaulted at the MODEL layer from the charge code so the eight line-raising services can't forget it) — a classification beside the rate, never a pointer the totals re-derive through. **The rate is picked, not typed**: read-only without `tax_codes.override` (withheld from `manager` — departing from the catalogue is an accounting act), enforced server-side by `App\Support\CatalogueTaxRate` from the items repeater's `mutateRelationshipData…Using` hooks. **That layer is load-bearing** — the repeater is relationship-backed, so rows never reach the page's `mutateFormDataBeforeCreate` and a guard written there protects nothing.
- **A document is written in the language its READER reads, and ONE class renders every one of them** (2026-08-27). All 13 `*PdfService` classes rendered in `app()->getLocale()` — the language of whoever pressed the button, or `config('app.locale')` for a scheduled run — so an operator working the panel in Arabic e-mailed an **Arabic invoice** to a retailer whose accountant files in English, and could produce the other copy only by changing their own UI language, downloading again, and changing it back. `App\Support\Pdf\DocumentLocale::resolve()` answers in order — **what the operator PICKED** on the download modal → the **RECIPIENT's** stored `locale` → the current request → `config('app.locale')` — each tier **clamped to `SetLocale::SUPPORTED`** (the ONE list) because an unsupported value does not throw: `__()` falls silently into the fallback locale, so the document renders in English while every other signal says Arabic. **The locale wraps the DATA resolution, not just the template** (`DocumentLocale::in()`, with `finally` so a throwing template cannot leave the operator's panel switched): `CamStatementPdfService` picks `name_ar` over `name_en` while building its facts and every service composes `__()`-derived labels into its view data, so a wrapper around `View::make()` alone yields an Arabic body under English headings. **On the API the request WINS instead** — the caller IS the recipient, `SetApiLocale` already resolved `Accept-Language`, and letting `tenants.locale` override it would mean a tenant who switches the mobile app to English keeps receiving Arabic PDFs with no way to change it; `?lang=` is the explicit override. **The e-mailed invoice follows the TENANT and the e-mail body follows the READER** — a tax document is addressed to the company and must not arrive in a different language depending on which portal login was notified. **`tenants.locale` was fillable on nothing and written by no screen**, so `preferredLocale()` had answered null for every tenant since the column shipped (2026-08-12): the mechanism was present and inert, the shape [[project_settings_screen_inert_bug]] records. It is now fillable, on the tenant form and the importer, and audited (`admin.fields.locale`, `VERBATIM_VALUES` — a language names itself the same way in every language). **Vendors and employees got the column the next day** (`2026_08_28_100000`), because the 2026-08-12 migration had chosen the set that receives a NOTIFICATION and a document goes somewhere else: a purchase order and a **withholding certificate** go to a SUPPLIER — the certificate being the document they hand their own accountant to claim tax already deducted from them — and a **payslip** goes to a PERSON. Neither model is `Notifiable`, so neither implements `HasLocalePreference`; `preferenceOf()` reads a plain `locale` attribute for exactly that case, which is why the column alone was enough and no call site changed. **All five `locale` columns are now in `ValueSets`** (derived from `SetLocale::SUPPORTED`, never re-listed), because the failure is silent in BOTH directions — `__()` falls through an unknown locale into the fallback language and `resolve()` skips the tier — so a typo'd `fr-CA` leaves the column looking set and every document rendering in English. `locale` joined `CLASSIFICATION_SUFFIXES`, so a sixth such column cannot ship unregistered. The **clamp still matters after the guard**: it defends rows written before the registration and anything a `saveQuietly()` or a migration writes, which is what a guard at the write cannot reach backwards into.
  **`App\Support\Pdf\PdfDocument` is the only thing that constructs mpdf.** The thirteen copies had drifted — two used 14mm margins where eleven used 12, two set 10pt where eleven set 10.5 — so *how these documents are typeset* was a thirteen-file edit nobody would make. Page geometry belongs to the renderer and **NOT to a template's `@page` rule**: every template set its own in px, which silently overrode mpdf's margins and left no room beneath the body, so the running footer now on every document rendered **nowhere at all** until the rules were removed. That footer carries the document's own reference and `page x of y` — a loose sheet of somebody's ledger with no number on it cannot be filed or challenged — and a cancelled/void/bounced document is **watermarked**, because a printed void invoice and a payable one differed by a small pill in the corner. **The font is IBM Plex Sans Arabic, checked into `resources/fonts/`**: mpdf bundles exactly one Arabic face (XB Riyaz, a Persian display family) and it broke the joins in ordinary Egyptian vocabulary — «تاريخ الاستحقاق», on the invoice's due-date line. One family across both scripts, so `autoLangToFont` is **off**: script detection exists to swap fonts for a family that cannot render a run, and ours renders both. A document font cannot be a CDN or install-time dependency — a box that cannot fetch it does not fail loudly, it silently issues invoices in a substituted face.
  **Six templates each carried ~150 lines of near-identical CSS** and had drifted the same way; `resources/views/pdf/layout.blade.php` + `_styles` + `_issuer` is that shell once, with the palette in `App\Support\Pdf\DocumentTheme`. **A `@section` body is evaluated BEFORE the layout renders**, so it can use nothing the layout defines — reaching for `$isRtl` there is an undefined-variable fatal, and the layout carries a `?? DocumentLocale::isRtl()` fallback for any caller that renders a template without the renderer. **`PdfDocument::html()` is the test seam**, for the reason `viewData()` is: a test that must inflate a PDF's compressed streams to find out whether the invoice says «فاتورة» will not be written, and the one written instead asserts on the service's inputs and proves nothing.
  **The look is DIRECTION D, chosen 2026-08-28 from four drawn side by side** (`/design`, working files in `storage/app/design/`) — a restrained ruled ledger, a dense administrative grid, a formal letterhead, and the brand-forward one the operator picked: **a full-bleed navy band carrying the mall's identity, and the balance set apart in an amber panel of its own**. Adopting a whole new direction was an edit to `DocumentTheme` + `_styles` + `layout`, not to twelve templates — which is the entire return on having built the shared system first. **The bleed is the difference between a masthead and a coloured box**, and mpdf has no per-element bleed, so the PAGE carries no side margin (`PdfDocument::bleed()`) and `.page-body` supplies the body's own. That makes it a call a service must remember, failing in the worst available way — the document still renders, still balances, and looks like a *rendering fault* rather than a missing line, so nobody would file it as one. `PdfLayoutBleedsConformanceTest` gates BOTH directions (mutation-proved), because the opposite mistake runs the payslip and the four financial statements edge to edge. **The tradeoff was stated when it was picked**: heaviest of the four on ink, weakest in greyscale — so the band is the ONLY large ink field, `ACCENT` is spent on exactly one figure per page, and `DUE`/`ACCENT` are separated in LIGHTNESS as well as hue so a photocopy still reads. `BAND_MUTED` is the one colour with a single permitted background; on paper it is grey-on-white. **Still IBM Plex Sans Arabic**: the mockups used Space Grotesk + Cairo, and Google publishes both only as VARIABLE fonts, which mpdf renders at one instance — no bold. One family covering both scripts was worth more than the mockup's exact face. Arabic needs its own metrics for anything Latin typography sizes by cap-height: the label size steps up one notch under RTL, and the status chip's padding does too — «مدفوعة جزئيًا» had its tashkeel clipped by the chip's own edge at the Latin value.
  **Operator-typed text keeps its OWN direction** (`App\Support\Pdf\Bidi`). The bidi algorithm resolves a NEUTRAL character — a full stop, a `+` — by what surrounds it, so an Arabic document rendered `.Issued in error; voided same day` and `201808046413+`. Both shipped, and both are **intermittent**: whether the stop moves depends on what else shares the line box, which is why they survived review. `isolate()` fences a value with the mark matching its FIRST STRONG character (so «الغرير للتجارة LLC» is Arabic); `isolateLines()` does it per line for a block, so a paragraph whose first line is Arabic and whose second is an IBAN does not resolve the IBAN as RTL. **Marks (U+200E/U+200F), not isolates: mpdf implements neither U+2068 FSI nor `<bdi>`** — measured, and both leave the run reordered with the isolate characters swallowed, which is worse than nothing because it looks handled. A leading `−` needs no marks at all if it is written AFTER the currency (`EGP −25,000.00`), where two LTR runs bracket it.
  Three gates: `PdfLocaleConformanceTest` (every public method returning a document takes `?string $locale`, derived from disk; mpdf constructed in one place), `PdfDocumentConformanceTest` (now follows `@include` **transitively** — it would otherwise sweep twelve documents and miss the only file that sets `letter-spacing` for all of them — and understands a variable DERIVED from `$isRtl`, checked by mutation so the escape hatch cannot be abused), and `DocumentsCarryTheMallLogoConformanceTest` (follows the shared issuer partial rather than requiring the include per file). **Both of the latter two had a prose false-positive**: they grep raw source, and a docblock mentioning `IssuingEntity::forView()` or discussing `text-transform` was read as code — a gate that fires on a sentence is one that gets weakened rather than fixed. (`ADocumentIsWrittenInItsReadersLanguageTest`, `TheDownloadButtonAsksWhichLanguageTest`.)
- **A document may call itself a TAX invoice only when the issuer states a registration, and "is it SET UP" is a gate, not a screen** (2026-08-25). Both now read `SlaResolver::clockFor()` for the CANONICAL clock names (neither module owns that vocabulary) and both **freeze** the answer on the row — `facility_work_orders.sla_clock` and `tenant_requests.sla_clock` — because a pending SLA is re-read on every breach scan, so resolving at read time would re-time every running job the moment the setting changed. **A clock is only half of it: whatever MEASURES the overrun must read the same stored clock.** There are FOUR such measures, not two — `FacilityWorkOrder::daysOverSla()` (it prices a GL penalty), `FacilityWorkOrder::hoursOverSla()` and `::hoursOverResponseSla()` (frozen onto the `sla_penalties` row, quoted in the breach bell and its email, printed on the list) and `TenantRequest::hoursOverSla()` (it words the tenant-request bell) — or the operator is told a three-hour failure is sixty-seven hours old. The first got its branch when the calendar shipped and the last a commit later; the middle two were missed for a week, so ONE penalty row carried an overrun measured two different ways. **Derive a list like this by grep, never from the diff you just wrote** — an invariant enumerated from a diff certifies the coverage you happen to have added. On the working clock a breached figure floors at 1 (a breach that fell entirely across a weekend is not "0 hours late"); on the calendar clock 0 still means "less than an hour", which is a different claim. Ships **off**: the setting is empty until the operator rules on which priorities are office work. **There WAS no morph map when the rename shipped**, so the two rename migrations (`2026_08_15_140000`, `2026_08_15_150000`) backfill 7 polymorphic columns by FQCN; the second one *fails* rather than completes if any row is left pointing at a class that no longer exists, because `LedgerPoster::sync()`'s answer to an unresolvable `journal_entries.source_type` is to void and re-post. **There is one now** (`App\Support\MorphMap`, installed the same day by `2026_08_15_170000` and enforced with `Relation::enforceMorphMap()`, which also turns on `requireMorphMap` so an unmapped class THROWS rather than leaking a name) — polymorphic columns store an **alias**, so never compare one against `::class`, and `MorphMapConformanceTest` gates completeness. This sentence read *"there is no morph map"* in the present tense for nine days after the map existed, which is exactly the trap it warns about.
