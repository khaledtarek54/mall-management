# Atriom — working guide for AI / dev sessions

Egyptian mall-management ERP · Laravel 13 · PHP 8.4 · Filament 4 · MySQL (prod/local) / sqlite `:memory:` (tests).
Operator **Eltizam** runs malls for owners (**Jawad**); **tenants** are the retailers.

**[docs/README.md](docs/README.md) is the index of the whole documentation tree** — read it if you are looking for something and do not know where it lives. **Read [docs/OVERVIEW.md](docs/OVERVIEW.md) first**, then the relevant **[docs/modules/NN-*.md](docs/modules/README.md)** before changing any module's logic — each has *Business rules*, *Extension points (how to change safely)*, and *Gotchas*.

**The tree was consolidated 2026-08-19** from **201 markdown files to 85** (excluding the handbook build source), and it is kept to four questions: *how the system works* (the six docs at `docs/` root) · *how each module works* ([`docs/modules/`](docs/modules/README.md)) · *what is missing* ([`docs/gap-analysis/README.md`](docs/gap-analysis/README.md) — **ONE** document, vs Yardi + the FM specialists + Odoo) · *how to run it* ([`operations/`](docs/operations/), [`qa/`](docs/qa/README.md), [`integrations/`](docs/integrations/), [`api/`](docs/api/MOBILE-API.md)). Everything else — completed implementation plans, per-module audit rounds, point-in-time sweeps, session workbooks, and a second and third description of the money model — was removed; git has it. **Do not re-create a parallel doc set:** if a topic already has a home, edit that file rather than adding a new one beside it, because the reader cannot tell which of two documents is current and the stale one costs more than the missing one would.

**Before go-live:** [docs/operations/GO-LIVE.md](docs/operations/GO-LIVE.md) — the single gate: every configuration item, credential and unanswered question, verified against the code (2026-08-11). The code is not the blocker.
**Before STAGING:** the ordered runbook is [docs/operations/STAGING-CUTOVER.md](docs/operations/STAGING-CUTOVER.md) (eight steps, links out rather than restating) and the box itself is [docs/operations/STAGING.md](docs/operations/STAGING.md) — a staging box is gated on none of that. It has its own `.env` deltas, one posture decision (demo data vs production restore), and a set of `atriom:health` rows that are *supposed* to be red there. `APP_ENV=staging` is a third tier, not "production-ish": `App\Support\Deployment` is the ONE reading of which tier a box is, and an unanticipated env name inherits the stricter treatment.

**Orientation:** [docs/PROJECT-MAP.md](docs/PROJECT-MAP.md) (generated census — what exists + what's covered) · [docs/ROADMAP.md](docs/ROADMAP.md) (**the single** prioritized list: go-live + FRD + accounting) · the visual handbook — read it **in the panel at `/admin/handbook`** (built by `npm run build`), or as source: [the whole system on one page](docs/visual/map.md), [a month in the life](docs/visual/scenarios.md).

## Conventions — do these
- **Tests:** `vendor/bin/pest --parallel` (Pest 4). Keep it green. Add a regression test for every bug fix in `tests/Feature/Regression/`; scenario tests live in `tests/Feature/Scenarios/`.
- **CI auto-runs are PAUSED** (2026-07-29, owner's call — the pipeline is too slow for the push loop). `.github/workflows/ci.yml` fires only on `workflow_dispatch`. So the conformance gates (PropertyIsolation, GlRegistry, MediaPrivacy, AdminSmokeManifest, **DashboardLayout**, PostingDateGuard, VatRateSetting, **ActionAuthz**, **QueueJobSafety**, **ConcurrencyPolicy**, **RecordStateRefresh**, **PhpExtensions**) + PHPStan + Playwright + `composer audit` are **ADVISORY**: nothing blocks a bad change. **Keep `pest --parallel` green locally before every push** — a red push is silent, not a red check.
  - **The jobs themselves were repaired 2026-07-29** and a manual run now actually works: `gh workflow run ci.yml`. All four had been failing on *every* run since ≥2026-07-23 for non-product reasons — `composer audit` missing `--locked` (it audited nothing, ever), PHPStan reading a baseline with **absolute paths** (green on one laptop, red everywhere else), and two timeouts set below the real runtime. Worth a manual run before anything risky.
  - **Cost, measured 2026-08-10: the suite is ~1.5 min** — **795s → 75–97s (~9×)** on the same ~3.68k cases (`pest --parallel`, 10 workers; the spread is background load, so measure on a quiet machine or the numbers lie by 3×). Two independent fixes got it there, and the old note here — ~20 min, blamed on migration replay, with `php artisan schema:dump` as the lever — was **wrong on all three counts**. Migrating 170 migrations into sqlite `:memory:` costs ~1.5s per worker, ~0.3% of the run. The real cost was `RolesPermissionsSeeder`, called from ~230 `beforeEach` blocks (~1,700 test cases) at **925ms a call**: spatie forgets its permission cache on every `saved`, and `Permission::findOrCreate()` reads back through that cache, so building the 182-key catalogue one row at a time reloaded it 182 times. Bulk-inserting the rows and wiring role grants in one pass took it to **11ms** with a byte-identical RBAC end state — verified by diffing both seeders' role→permission dumps (14 roles, 182 permissions, every grant equal), and pinned by `RolesPermissionsSeederBulkWriteTest`. That test warms spatie's cache against an empty catalogue first, because the bulk write's one real hazard is skipping the `saved` hook that would have invalidated it.
  - **The second fix was shape, not speed: Pest parallelises per FILE.** `AllFiltersSweepTest` swept every admin table in ONE 80s case, so it pinned one worker while nine idled and set the floor under the whole suite — no optimisation elsewhere could get below it. It is now sharded across `AdminFilterSweepShard{1..4}Test.php` off shared scaffolding in `Tests\Support\FilterSweep` (a class, not file-scope helpers: a parallel worker only loads the test files it owns, and re-declaring them per shard is a fatal redeclaration). paratest's per-method `--functional` mode would remove the need — but it **crashes** in Pest's `WrapperRunner` (`realpath()` on a `file::method` string), so files are the only unit of parallelism we have. **Sharding costs CPU to buy wall-clock** (each shard re-seeds `DemoSeeder`), which only pays while a file dominates the critical path — past that the binding limit is total CPU ÷ workers, and the answer is to cut work, not split it further.
  - **If the suite slows down again, profile before theorising** — `pest --parallel --log-junit <file>` gives per-case times. Two traps: they are wall-clock under 10-way contention and overstate solo cost by ~5-6× (confirm any suspect file by running it alone), and a run sharing the machine with another suite inflates *everything* ~3.7× uniformly, which reads exactly like a real regression. Known next levers, both measured, neither taken: `DemoSeeder` writes **1,287 activity_log rows** (suppressing them is −21% of its runtime), and it issues **18k queries for 274ms of actual SQL** — the cost is PHP per-query overhead, most visibly ~1,400 repeated `account_mappings` lookups and ~560 `accounting_periods` lookups in the GL posting path, which memoising would speed up in production too.
  - **Suite exits 255 with NO output at all?** That is almost always two test files declaring the same file-scope helper — a fatal redeclaration during collection, before any test runs. It has happened three times (`makeViolation`, `optionOn`, `annualPctLease`). `--parallel` hides it (each worker only loads its own files) and every instinctive recovery — re-run, run the directory, add a `--filter` — loads everything and dies identically. **The one command that works:** `vendor/bin/pest tests/Feature/Scenarios/TestHelperUniquenessConformanceTest.php` — a path-scoped run loads only that path, and the gate names both files. The fix is usually to *reuse* the existing helper, not rename yours; shared ones belong in `tests/Pest.php` or a class under `Tests\Support`.
- **Business logic** goes in single-action services (`app/Services`); keep controllers + Filament pages thin.
- **Docs are part of "done":** changing a module's logic → update its `docs/modules/NN-*.md` (+ `docs/OVERVIEW.md` if cross-cutting) **in the same commit**.
- **Local DB:** MySQL; reseed with `php artisan migrate:fresh --seed` after a feature (`DemoSeeder` = canonical demo data). **`LearningSeeder` is the empty-mall variant** — the same reference data `atriom:install` lays down, one property, 12 vacant units, 3 tenants and *nothing else*, so an experiment's own numbers are the only numbers on screen.
- **Commits:** push to `main` directly (owner's established preference). End commit messages with the `Co-Authored-By:` line.

## Invariants — don't break
- **Money / AR:** `Invoice::recomputeTotals()` is the single source of truth — `paid_amount = captured payments + credit_applied_amount + applied tenant credit (`TenantCreditApplication`) + netted security deposit (`DepositApplication`)`, `balance = total − paid_amount`. Never set `paid_amount`/`balance` directly elsewhere. **FOUR channels, and every calculation that decides "how much of this invoice is settled" must count all four** — adding one means also updating `Invoice::capturedCashPaid()` (none of the three non-payment channels is cash, so the void guard must exclude them), the cancel-invoice release (or the settlement strands on an invoice that left the books), and BOTH payment over-allocation guards (`Payment::assertInvoicesNotOverAllocated()` and `refitAllocationsToBalance()` — omitting one lets a payment over-settle an invoice another channel already paid, burying the excess as negative AR; that has happened once already). **Item-level allocation (`invoice_item_payment`, MF-06) is NOT a fifth channel** — it records how an already-counted settlement splits across the lines. `App\Support\InvoiceItemSettlement` derives every per-line figure from `paid_amount`, so the item outstandings always sum back to `balance`; never store a per-item balance, that is a second truth about the same money.
- **An invoice's debtor is DERIVED on the form, and is NOT an invariant of the model.** The invoice form shows `tenant_id` read-only beside the lease picker and `CreateInvoice` re-derives it from the lease on save — a disabled field's value still arrives in the Livewire payload, so trusting it lets a crafted request bill a party who never agreed to the charge (until 2026-08-17 a free tenant picker made that two clicks in the UI). **Do NOT promote this to a model-level equality rule** — that was tried on 2026-08-17 and the full suite refused it, correctly: `IssueInvoiceService::issue()` takes an explicit `$tenantId` so a violation fine, a bounced-cheque fee and a late fee carry the debtor stated on their SOURCE document, and a DRAFT invoice may be freely re-homed to another lease before it is issued. Both are deliberate. The rule holds only on the one path where "the form never states a debtor" is unambiguously true.
- **General ledger:** `LedgerPoster::JOURNALIZERS` is the **single registry** of what posts to the GL; all four dispatch paths (real-time hooks · `accounting:sync-ledger` sweep · close gate · `billing:reconcile` drift check) **derive** from it via `LedgerPoster::sources()` — never re-list them. New money source = one registry line + its `LedgerRealtimeSync::SOURCE_DATE_COLUMNS` entry; `GlRegistryConformanceTest` fails CI otherwise. **A GL test that calls `LedgerPoster::post()`/`sync()` directly proves only the journalizer's arithmetic** — at least one test per source must drive the real service + the sweep and assert the tie-out. (This exact gap let applied SLA penalties cut a vendor bill while posting nothing — see [modules/21](docs/modules/21-general-ledger.md#gl-registry-gate).)
- **Tax** on service charges; **base rent is VAT-exempt**. **Marketing levy 5%** of base rent (that one IS a lease term, so it stays in settings — and is now actually editable there: it had no screen at all until 2026-08-12, so "configurable" was a claim only a deploy could honour). Two separate questions, two separate homes: **which supplies are taxable** is `charge_codes.tax_code` — the accountant's ruling, a row, no deploy (where Yardi puts it too) — and **what that tax charges** is the `tax_codes` + `tax_rates` catalogue at `/admin/tax-codes`. A rate is a **dated rung**, never a column: `Vat::rateForType($code, $on)` resolves for the DOCUMENT's date, so a rise can be entered in advance and a back-dated invoice keeps the rate that was in force. `TaxSettings::vat_standard_rate` is GONE (2026-08-12) — settings hold policy, master data holds rates. The catalogue is **the operator's own `account.tax` sheet** ([docs/accounting/EGYPTIAN-TAX-CATALOG.md](docs/accounting/EGYPTIAN-TAX-CATALOG.md)): VAT · stamp · schedule · withholding, each in both directions — **never invent a row beyond it, and never drop one** (`TaxCatalogueConformanceTest` gates both). **Stamp + schedule were COMMISSIONED 2026-08-19** and a fresh install ships them on (an existing DB gets the posting role backfilled and stays off — a reseed must never reactivate a code the operator retired). The blocker was never mainly the accounts: all three journalizers threw the document's own `tax_code` away — the invoice one summed every line's tax into one accumulator and credited `vat_payable`, the vendor-bill and expense ones hard-coded `vat_recoverable` — so an active stamp code would have put 20% of a supply on the VAT return, under the VAT liability, balanced and tied out. **Tax now groups by the tax code's own posting role**, exactly as revenue groups by the charge code's, with VAT as the floor for a document naming no code. The asymmetry is the real content and must not be flattened: output stamp/schedule are LIABILITIES, input stamp/schedule are **EXPENSES** (`stamp_tax_expense` / `schedule_tax_expense`), because neither has a credit mechanism the way input VAT does — copying the VAT shape there grows a receivable nobody can ever collect. `TaxCode` still refuses to activate a taxable code with no rate or no posting role, so an incomplete catalogue is inert rather than a trap. Activation grants nothing on its own: a code taxes a supply only when a CHARGE CODE points at it, which is the accountant's ruling and a row. **Every origination point calls `App\Support\Vat::rateForType($code, $on)`** (or `Vat::onType()`); a service calling `standardRate()`/`on()` directly can't see the ruling and fails `ExemptChargeTypesAgreeAcrossPathsTest`, and a literal rate anywhere fails `VatRateSettingTest`. `Vat::EXEMPT_TYPES` + `Vat::DEFAULT_STANDARD_RATE` are the FLOOR for an unseeded catalogue, not the policy — they must resolve identically to the seeded catalogue (`ChargeCodeVatTreatmentConformanceTest`), exactly as `InvoiceJournalizer::REVENUE_ROLE` floors the posting roles. Only **origination** reads any of it: an issued invoice keeps the rate it was billed at, so neither a rate change nor a treatment change ever rewrites history. **For a recurring charge, origination is BILLING, not the day the schedule row was written** — `charges.vat_rate` is an OVERRIDE and null is the normal state, with `Charge::resolvedVatRate($on)` the one place that answers what it bills on a date. Storing the catalogue's answer on the row is what broke this until 2026-08-12: the rate froze for the life of the lease, so a rise entered in advance reached every one-off charge and **never reached rent or service charge** — most of the money — and the amendment path carried the stale rate onto the new row too. Proven, not argued: with a rise to 20% effective 1 Sept, the resolver answered 20 for a September document while the September invoice billed 14. `vat_applicable = false` still wins over both, and after the backfill it is the ONLY thing holding an untaxed row (`VatRiseReachesRecurringRentTest`). **A document line records WHICH tax it carried** (`invoice_items.tax_code`, defaulted at the MODEL layer from the charge code so the eight line-raising services can't forget it) — a classification beside the rate, never a pointer the totals re-derive through. **The rate is picked, not typed**: read-only without `tax_codes.override` (withheld from `manager` — departing from the catalogue is an accounting act), enforced server-side by `App\Support\CatalogueTaxRate` from the items repeater's `mutateRelationshipData…Using` hooks. **That layer is load-bearing** — the repeater is relationship-backed, so rows never reach the page's `mutateFormDataBeforeCreate` and a guard written there protects nothing.
- **Money records are NEVER deletable — not even by super_admin** (operator decision 2026-07-31). Invoice, Payment, JournalEntry, CreditNote, VendorBill, Expense, DepositTransaction, Payroll, PostDatedCheque: no Delete/ForceDelete action, no `{module}.delete` permission, and a model-level refusal (`RefusesDeletionOfCommittedRecords`) as the backstop. Correct them through their own workflow — cancel / void / credit note / reverse — which leaves a document an auditor can follow. An UNCOMMITTED record is still removable (a draft journal entry, a payment that never became money), which is what keeps `CreatePayment`'s orphan rollback working. Registry = `App\Support\DeletionPolicy`, which **derives** the tiers from an attribute on each model (2026-08-15) — you classify a model by writing `#[NeverDeletable(correction: …)]` / `#[DeletableWhenUnused(blockedBy: […], instead: …)]` / `#[DeletionAllowed(reason: …)]` on the class, not by editing an array; `DeletionPolicyConformanceTest` fails the build if a Delete button or permission reappears. **Master data with history is refused too** (`#[DeletableWhenUnused]` — Tenant, Vendor, Lease, Unit, Asset, Employee): deletable only while nothing references it, otherwise deactivate. This follows Yardi/MRI/Entrata, which all refuse rather than warn — the damage lands on the reports and audit trail that referenced the record, not on the record itself. `blocked_by` relations are verified to EXIST by the gate (a typo'd relation blocks nothing and looks identical to a working guard). Note `Unit` uses `allLeases` (the pivot), not `leases`. **Every model is classified** — `#[NeverDeletable]` / `#[DeletableWhenUnused]` / `#[DeletionAllowed]` (with a stated reason) — and the gate fails on an unclassified one, because it discovers models by globbing `app/Models` rather than by reading the registry, so a new model forces a decision rather than inheriting a default. Before adding `#[NeverDeletable]`, check for a real deletion call site in `app/`: guarding a row a service legitimately deletes breaks the workflow instead of protecting it (that check saved the credit-note un-apply, the tenant-credit reversal, the owner-statement rebuild, and the advance-repayment reversal). Two models are deliberately `#[DeletionAllowed]` despite carrying history — `UtilityMeter` and `FixedAsset` — because soft-delete IS their tested retirement path and the GL/trend already handle it; both omissions are annotated in the registry. **Everything else: delete = super_admin only**; bulk-delete is off project-wide (opt-in via `$bulkDeletable`). CRUD gating via `RoleGatedActions` on `{module}.{action}` permissions (`RolesPermissionsSeeder`).
- **Property isolation:** every module is isolated to the selected property. **Reads:** resource tables auto-scope; scope any cross-property Filament select via `App\Support\TenantScope::selectable*` / `visibleAssetIds()` (never `currentAssetId()` alone — null in All-mode leaks); "All Properties" pseudo-asset = `Asset::ALL_PROPERTIES_CODE`. **Writes:** if a form exposes/derives an editable `asset_id`, guard it with `GuardsAssetInScope::assertAssetInScope()` on create+edit (Filament only stamps `asset_id` on create, never update). Shared-vs-isolated register = `App\Support\PropertyIsolation`; the `PropertyIsolationConformanceTest` gate fails CI if a new model/resource ships unclassified/unscoped/unguarded. **The property field itself is `App\Support\Filament\PropertyField::make()`, never a bare `EntitySelect::make('asset_id')`** — with a real mall selected `visibleAssetIds()` is `[currentId]`, so a blank property is a bare **403** from `assertAssetInScope((int) null === 0)` and a foreign one fails `EntitySelect`'s label lookup at validation. Both refusals were already airtight; what 7 screens did was OFFER those options anyway, so "Consolidated (all)" on a filled-in journal entry ended at a 403 wall and the six financial statements ran under a *"Consolidated (all)"* caption while `TenantScope::reportAssetIds()` clamped every pick back to the selected mall — right figures, wrong caption, which nobody re-checks. The component pins + disables + **dehydrates** (a disabled input is not submitted, so without it the pinned value never reaches the model); pass an extra lock as `$alsoDisabledWhen`, because chaining `->disabled()` after it silently unpins the field. `PropertyField::free()` is the opt-out for the three PORTFOLIO-CONFIG screens in `PropertyField::PORTFOLIO_LEVEL` (posting map · departments · owner requests), each with a reason. **The pin is a UI truth, not a gate** — the value still arrives in the Livewire payload, so every `assertAssetInScope()` stays. `PropertyFieldPinnedConformanceTest` RENDERS each create form and reads the built component's state (a call site can chain `->disabled(false)` and look correct in source), and fails on a stale exemption. **Read [docs/PROPERTY-ISOLATION.md](docs/PROPERTY-ISOLATION.md) before adding a property-owned module.**
- **You cannot grant access you do not hold.** `users.create`/`users.edit` are held by `manager`, `hr` and `mall_admin` as well as super_admin, and the user form's property-assignment field is what grants access to a mall — so until 2026-08-17 a manager pinned to Mall A could open their OWN record, add Mall B and see it. Privilege escalation through an ordinary CRUD screen, demonstrated through the real form. `UserResource::enforceGrantableAssetsRule()` reverts BOTH directions (a restricted grantor can neither grant nor REVOKE a property they cannot see) and logs the attempt to `AccessControlAudit` — mirroring `enforceProtectedRolesRule()`, which this screen already used for the same class of problem. It runs in `afterCreate`/`afterSave`, not in a `mutateFormData…` hook, because a relationship Select saves from COMPONENT STATE via `saveRelationships()` and never reads mutated form data. Measured against `AssignedAssets::idsForCurrentUser()`, NOT `TenantScope::visibleAssetIds()` — the latter collapses to the SELECTED property, which would stop an hr user holding two malls granting the one they are not looking at. The picker itself stays portfolio-wide (`->acrossProperties()`): a narrowed option list is not a gate, since the assignment arrives as a Livewire payload.
- **Auth surfaces:** `/admin` = `User` + spatie roles · `/portal` = `TenantUser` (multi-user; only `is_admin` may write) · `/api/v1` = Sanctum `tenant-api` against `Tenant`. Cross-tenant API returns **404** (no existence enumeration).
- **A draft is not a document — the tenant never sees one.** "Whose row is this?" and "has this been raised?" are **two questions**, and scoping through `$request->user()->invoices()` only answers the first. Every tenant-facing read must also narrow with `->visibleToTenant()` (`App\Support\TenantVisibility` + the `HidesDraftsFromTenant` concern); the relationship itself must NOT be narrowed, because admin and the GL read the same one and need every row. `invoices.status` and `credit_notes.status` both **DEFAULT to `'draft'` at the column**, so a draft is what any create that omits the status produces (`CreditUnearnedBillingService` does) — this is the normal case, not an exotic one. It leaked on **seven surfaces at once** (list · show · invoice PDF · Statement of Account · `pay-demo` · `paymob-session` · the portal invoice table), and `?status=draft` let a tenant enumerate them. The **visible** set is derived — `ValueSets::allowed()` minus `HIDDEN` — so a new status is visible by default and must be hidden deliberately; the scope **excludes** rather than allowlists, so a legacy/imported status still reaches its tenant (losing a real document from someone's history is the worse failure). Only `draft` is hidden: a `cancelled` or `written_off` invoice still explains a number the tenant remembers. **The portal and `/api/v1` are the same surface with different renderers** — fix both or neither. `TenantNeverSeesADraftTest` pairs every refusal with a control that must succeed, because a scope that hid everything would satisfy the refusals alone and read as a pass.
- **`visible()` is NOT an authorization gate.** (`ActionAuthzConformanceTest` now gates this: every `Action::make()` chain under `app/Filament` carrying an `->action()` must also carry `->authorize()`/`abort_unless`, or be registered in `App\Support\ActionAuthz::EXEMPT` with a reason.) **Correction 2026-07-31 — the "still dispatchable" half of this was WRONG on the version we ship.** `mountAction()` does check `isDisabled()`, and `CanBeDisabled::isDisabled()` returns true when `isHidden()` does (`vendor/filament/actions/src/Concerns/CanBeDisabled.php:24`), so on **Filament v4.11.8 a `visible()`-only action IS refused at dispatch**. Found by mutation-testing the module-08 fix: deleting CAM's `abort_unless` left `CamActionAuthzTest` fully green — those tests never exercised the gate they describe. **The second layer is now real, and global (2026-08-12).** `Action::make()` resolves through the container, so `Filament\Actions\Action` is bound to `App\Support\Filament\AuthorizedAction`, which runs `abort_unless($this->isAuthorized(), 403)` inside `call()` — the check Filament's own `Action::call()` never performed. That closes FS-23 at one seam instead of in 76 files: `->authorize()` folds into `isHidden()` folds into `isDisabled()`, so on the letter of it `visible()` and `->authorize()` were one layer, and the 76 write actions gating with `->authorize()` alone (journal-entry post/void, void_invoice, period close) had no second one. `isAuthorized()` returns true when nothing was declared, so the ~500 actions gating with `abort_unless` are untouched. `ActionCallIsAuthorizedTest` pins the refusal AND the binding, so a Filament release switching `make()` to `new static` turns the build red rather than quietly removing the layer. **Double-gate anyway**, for a reason that survives the correction: `->authorize()` is a stated intent, while hidden-implies-disabled is an upstream implementation detail that can change in a release and would silently reopen every `visible()`-only write at once. `FilamentActionDispatchContractTest` pins that upstream behaviour so an upgrade that changes it turns the build red; `ActionAuthzConformanceTest` enforces the layer we control. Every write action must gate in **both** `visible()` (the UI) and `action()` (`abort_unless(...)` — the actual gate); name the predicate once so they can't drift. **In tests, neither `->callAction()` NOR `mountAction` proves the `action()` gate** — `callAction()` asserts visibility first, and `mountAction` refuses hidden actions for the reason above, so both go green whether or not the gate exists. To prove a gate, remove it and watch the test fail; to test one, assert the predicate directly. And always pair a refusal test with an authorised control — a refusal passes just as happily when the dispatch is a no-op.
- **A screen is SEVERAL Livewire components, and a success toast is not a refreshed screen.** A record page, each relation manager under it and each header widget are separate components with separate lifecycles; Livewire 3 re-renders only the one that handled the click (the widgets blade mounts each with a STABLE `key()`, which is exactly what tells Livewire to leave a child alone). Two seams fix the two halves. **(a) `refreshFormData()` never re-reads.** It refills from `$this->getRecord()->attributesToArray()` — the page's IN-MEMORY copy — so behind any service that re-reads its subject as a locking read into a new instance, which is what EVERY money service here does and must do, the call refills the same stale values and does nothing. Proven, not argued: `EditInvoice::void_invoice` left the form reading `issued` / `10,000.00` while the row read `cancelled` / `0.00`, with `refreshFormData(['status','balance','notes'])` sitting in the action. **Nineteen call sites across eight money pages had that shape — one of them, the payroll-lines listener, re-read first and was the only correct one — and the suite was green throughout, because every test asserted `$invoice->fresh()->status` — the ROW — and none asserted the form.** `App\Support\Filament\RefreshesRecordState` re-reads before refilling; use it on any Edit/View page that refills, and `RecordStateRefreshConformanceTest` fails the build otherwise. **(b) nothing tells the rest of the screen.** `App\Support\Filament\RecordChanged::EVENT` is the ONE event (deliberately not per-module — a second name is a second thing to forget), announced automatically after every action: `Action::make()` resolves to `AuthorizedAction`, and `CreateAction`/`EditAction`/`DeleteAction` resolve to the three `Announcing*Action` bindings, because those are subclasses and never saw the `Action` binding. A page opts IN with the trait and declares `derivedStatePaths()` — **DERIVED fields only**, since refilling a field the operator is typing discards their edit; declaring none is still useful, because the re-read alone fixes a `TextEntry->state(fn ($record) => …)` that resolves at render time. A widget opts in with `RefreshesOnRecordChange` (an empty listener IS the refresh — Livewire re-renders for any listener call). **A download announces nothing** — the seam tests the action's RETURN VALUE for a `Response` rather than keeping a list of read-only action names.
- **Search:** every searchable model carries a fold-normalized `search_text` blob (`App\Models\Concerns\HasSearchText`), and BOTH sides go through `App\Support\Search\SearchText` — the stored value and the operator's query. Folding one side matches nothing. Resources search `['search_text', 'tenant.search_text', …]` and **never a raw column**: a path pointed at `tenant.name` compares a folded query against an unfolded value, so it silently misses exactly the Arabic spellings the fold exists to fix («شركة»/«شركه», «أحمد»/«احمد») while still working for plain ASCII — which is what anyone spot-checking it would try. **The blob is a pure function of the row's OWN attributes** — never reach through a relation, or renaming a tenant strands every invoice blob that quoted it. The Dr/Cr lines per journalizer are deliberately NOT generated: they resolve through `ChargeCode::roleFor()` at runtime, so any map would be a guess drawn as a diagram.
- **PM compliance is DERIVED, never stored** (2026-08-20). `FacilityWorkOrder::pmComplianceState()` answers `on_time` · `late` · `overdue` · `due` from two columns that existed all along — `scheduled_for` **is** the plan's due date, because the generator copies `next_due_date` onto the order — and returns null for a corrective job (it answers to its SLA) or a cancelled cycle. `overdue` is a function of TODAY, so storing it would need a sweep and would go wrong on a day when nothing happened. **Completing at 16:00 on the due day is ON TIME**: compare whole days, or a datetime-vs-date comparison calls every afternoon completion late. The three scopes (`pmOnTime`/`pmLate`/`pmOverdue`) are the query twins the column, both filters and `ServicePlan::complianceRate()` all share so they cannot drift; the list variant `withComplianceCounts()` is pinned by a test to return the same figure as the record. A cycle still inside its window is EXCLUDED from a plan's rate, and a plan with nothing settled has NO rate — 0% and 100% are both inventions. **Strict, with no tolerance window** — a stated deviation from Maximo, because one global tolerance is wrong for both a weekly round and an annual overhaul, and strict never overstates.
- **A work order is a COST OBJECT and must NEVER become a GL source.** `FacilityWorkOrder::recomputeCosts()` (2026-08-20) is the single source of truth for what a job cost — written like `Invoice::recomputeTotals()`, with THREE channels that each call it: `facility_work_order_labour` (hours × the craft rate, **frozen at entry**), approved/recorded part draws, and vendor bills + expenses carrying `facility_work_order_id`. Never set an `act_*` column anywhere else; adding a fourth channel means adding it to the method AND wiring that model's events. **Net of VAT and net of an applied SLA penalty**, cancelled documents excluded, and a document moved between jobs recomputes the job it LEFT. **The money is already in the ledger** — `StockMovement`, `VendorBill`/`Expense`, `Payroll` — so these columns are a management dimension over posted money: registering a journalizer would post every maintenance cost twice **and balanced**, which is why `WorkOrderIsACostObjectNotAGlSourceTest` gates it. For the same reason a report may not ADD work-order labour to the wage bill; it EXPLAINS part of it. Estimates are nullable and actuals default to 0, because "not estimated" and "estimated at nothing" are different claims and planned-vs-actual is the whole point. `job_value` is GONE — it duplicated `est_service_cost`, and the SLA percent basis now prefers the ACTUAL service cost once a bill lands. Tools are Maximo's fourth bucket, deliberately folded into service (a mall hires the lift, so it arrives as a bill).
- **A trade is a ROW, and it is the spine of the facility model.** `App\Models\Trade` (2026-08-20) classifies work orders, service plans AND equipment; `vendor->trades()` says who may be dispatched to it; `standard_hourly_rate` is the craft rate the work-order cost object reads. It replaced `category` — a `Select` fed from `__('admin.facility.categories')`, i.e. a **translation array**: not in `ValueSets` so the column was unenforced, un-extendable without a deploy in two languages, and hardcoded a second and third time in `EquipmentForm`/`EquipmentTable` with four trades missing from both. **Never re-introduce `category` on those three tables** — two columns answering "what kind of work is this" is two truths about one question. **A tenant picks a PROBLEM, not a trade**: `tenant_requests.category` is a subcategory of its `TenantRequestType` and only the *Maintenance* type's subcategories are trade codes, so `RaiseCorrectiveWorkOrderService::tradeForRequest()` RESOLVES it and yields null for a noise complaint — copying it across is what put `noise`/`parking`/`lease_copy` in the trade column for the whole of module 26's life. **Eligibility is a suggestion, compliance is the gate**: `Vendor::assignableOptions()` GROUPS the picker ("Does this trade" / "Other vendors") and never filters, because Filament validates a Select with `Rule::in` and refusing an unusual-but-legitimate pick is the worse failure; `Vendor::isDispatchable()` stays the only hard block. The yardstick is [docs/benchmarks/fm/](docs/benchmarks/fm/) — **IBM Maximo** for the work-and-asset core, **ServiceChannel** for the contractor loop.
- **Terminal records** are immutable: closed/cancelled maintenance, responded owner-requests.

**"Maintenance" is not an identifier in this system (2026-08-15).** The word meant five different things and only two of them were ever the same module, so it is now reserved for the four places it is plain English rather than a name:
- `units.status = 'maintenance'` — a unit out of service ("Under Maintenance")
- the `maintenance` expense / vendor-bill category — posts to `maintenance_expense`
- `TenantRequestType::Maintenance` — a maintenance request is one KIND of tenant request
- Laravel's own maintenance mode (`php artisan down`)

Everything else moved. Module 11 (tenant requests) → `requests.*` permissions, `Modules::enabled('requests')`, `config/requests.php`. Module 26 (facility) → `facility.*` permissions, `Modules::enabled('facility')`, models `FacilityWorkOrder` / `FacilityWorkOrderItem` / `FacilityWorkOrderPart` / `ServicePlan` / `SlaPenalty` over `facility_work_orders` / `service_plans` / `sla_penalties`. The SLA hours both modules read are `SlaSettings` (group `sla`) + `config/sla.php` — named for neither module on purpose, because naming shared settings after one consumer is what created the confusion in the first place. **There is no morph map**, so the two rename migrations (`2026_08_15_140000`, `2026_08_15_150000`) backfill 7 polymorphic columns by FQCN; the second one *fails* rather than completes if any row is left pointing at a class that no longer exists, because `LedgerPoster::sync()`'s answer to an unresolvable `journal_entries.source_type` is to void and re-post.
