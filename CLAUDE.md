# Atriom — working guide for AI / dev sessions

Egyptian mall-management ERP · Laravel 13 · PHP 8.4 · Filament 4 · MySQL (prod/local) / sqlite `:memory:` (tests).
Operator **Eltizam** runs malls for owners (**Jawad**); **tenants** are the retailers.

**[docs/README.md](docs/README.md) is the index of the whole documentation tree** — read it if you are looking for something and do not know where it lives. **Read [docs/OVERVIEW.md](docs/OVERVIEW.md) first**, then the relevant **[docs/modules/NN-*.md](docs/modules/README.md)** before changing any module's logic — each has *Business rules*, *Extension points (how to change safely)*, and *Gotchas*.

**The tree was consolidated 2026-08-19** from **201 markdown files to 85** (excluding the handbook build source), and it is kept to four questions: *how the system works* (the six docs at `docs/` root) · *how each module works* ([`docs/modules/`](docs/modules/README.md)) · *what is missing* ([`docs/gap-analysis/README.md`](docs/gap-analysis/README.md) — **ONE** document, vs Yardi + the FM specialists + Odoo) · *how to run it* ([`operations/`](docs/operations/), [`qa/`](docs/qa/README.md), [`integrations/`](docs/integrations/), [`api/`](docs/api/MOBILE-API.md)). Everything else — completed implementation plans, per-module audit rounds, point-in-time sweeps, session workbooks, and a second and third description of the money model — was removed; git has it. **Do not re-create a parallel doc set:** if a topic already has a home, edit that file rather than adding a new one beside it, because the reader cannot tell which of two documents is current and the stale one costs more than the missing one would.

**Before go-live:** [docs/operations/GO-LIVE.md](docs/operations/GO-LIVE.md) — the single gate: every configuration item, credential and unanswered question, verified against the code (2026-08-11). The code is not the blocker.
**Before STAGING:** the ordered runbook is [docs/operations/STAGING-CUTOVER.md](docs/operations/STAGING-CUTOVER.md) (eight steps, links out rather than restating) and the box itself is [docs/operations/STAGING.md](docs/operations/STAGING.md) — a staging box is gated on none of that. It has its own `.env` deltas, one posture decision (demo data vs production restore), and a set of `atriom:health` rows that are *supposed* to be red there. `APP_ENV=staging` is a third tier, not "production-ish": `App\Support\Deployment` is the ONE reading of which tier a box is, and an unanticipated env name inherits the stricter treatment.

**Orientation:** [docs/PROJECT-MAP.md](docs/PROJECT-MAP.md) (generated census — what exists + what's covered) · [docs/ROADMAP.md](docs/ROADMAP.md) (**the single** prioritized list: go-live + FRD + accounting) · the visual handbook — read it **in the panel at `/admin/handbook`** (built by `npm run build`), or as source: [the whole system on one page](docs/visual/map.md), [a month in the life](docs/visual/scenarios.md).

## Conventions — do these
- **Tests:** `vendor/bin/pest --parallel` (Pest 4). Keep it green. Add a regression test for every bug fix in `tests/Feature/Regression/`; scenario tests live in `tests/Feature/Scenarios/`.
- **CI auto-runs are PAUSED** (2026-07-29, owner's call — the pipeline is too slow for the push loop). `.github/workflows/ci.yml` fires only on `workflow_dispatch`. So the conformance gates (PropertyIsolation, GlRegistry, MediaPrivacy, AdminSmokeManifest, **DashboardLayout**, PostingDateGuard, VatRateSetting, **ActionAuthz**, **QueueJobSafety**, **ConcurrencyPolicy**, **RecordStateRefresh**, **PhpExtensions**) + PHPStan + Playwright + `composer audit` are **ADVISORY**: nothing blocks a bad change. **Keep `pest --parallel` green locally before every push** — a red push is silent, not a red check.
  - **The jobs themselves were repaired 2026-07-29** and a manual run now actually works: `gh workflow run ci.yml`. All four had been failing on *every* run since ≥2026-07-23 for non-product reasons — `composer audit` missing `--locked` (it audited nothing, ever), PHPStan reading a baseline with **absolute paths** (green on one laptop, red everywhere else), and two timeouts set below the real runtime. Worth a manual run before anything risky.
  - **Cost, measured 2026-08-10: the suite is ~1.5 min** — **795s → 75–97s (~9×)** on the same ~3.68k cases (`pest --parallel`, 10 workers; the spread is background load, so measure on a quiet machine or the numbers lie by 3×). Two independent fixes got it there, and the old note here — ~20 min, blamed on migration replay, with `php artisan schema:dump` as the lever — was **wrong on all three counts**. Migrating 170 migrations into sqlite `:memory:` costs ~1.5s per worker, ~0.3% of the run. The real cost was `RolesPermissionsSeeder`, called from ~230 `beforeEach` blocks (~1,700 test cases) at **925ms a call**: spatie forgets its permission cache on every `saved`, and `Permission::findOrCreate()` reads back through that cache, so building the 182-key catalogue one row at a time reloaded it 182 times. Bulk-inserting the rows and wiring role grants in one pass took it to **11ms** with a byte-identical RBAC end state — verified by diffing both seeders' role→permission dumps (14 roles, 182 permissions, every grant equal), and pinned by `RolesPermissionsSeederBulkWriteTest`. That test warms spatie's cache against an empty catalogue first, because the bulk write's one real hazard is skipping the `saved` hook that would have invalidated it.
  - **The second fix was shape, not speed: Pest parallelises per FILE.** `AllFiltersSweepTest` swept every admin table in ONE 80s case, so it pinned one worker while nine idled and set the floor under the whole suite — no optimisation elsewhere could get below it. It is now sharded across `AdminFilterSweepShard{1..4}Test.php` off shared scaffolding in `Tests\Support\FilterSweep` (a class, not file-scope helpers: a parallel worker only loads the test files it owns, and re-declaring them per shard is a fatal redeclaration). paratest's per-method `--functional` mode would remove the need — but it **crashes** in Pest's `WrapperRunner` (`realpath()` on a `file::method` string), so files are the only unit of parallelism we have. **Sharding costs CPU to buy wall-clock** (each shard re-seeds `DemoSeeder`), which only pays while a file dominates the critical path — past that the binding limit is total CPU ÷ workers, and the answer is to cut work, not split it further.
  - **If the suite slows down again, profile before theorising** — `pest --parallel --log-junit <file>` gives per-case times. Two traps: they are wall-clock under 10-way contention and overstate solo cost by ~5-6× (confirm any suspect file by running it alone), and a run sharing the machine with another suite inflates *everything* ~3.7× uniformly, which reads exactly like a real regression. Known next levers, both measured, neither taken: `DemoSeeder` writes **1,287 activity_log rows** (suppressing them is −21% of its runtime), and it issues **18k queries for 274ms of actual SQL** — the cost is PHP per-query overhead, most visibly ~1,400 repeated `account_mappings` lookups and ~560 `accounting_periods` lookups in the GL posting path, which memoising would speed up in production too.
  - **Suite exits 255 with NO output at all?** That is almost always two test files declaring the same file-scope helper — a fatal redeclaration during collection, before any test runs. It has happened three times (`makeViolation`, `optionOn`, `annualPctLease`). `--parallel` hides it (each worker only loads its own files) and every instinctive recovery — re-run, run the directory, add a `--filter` — loads everything and dies identically. **The one command that works:** `vendor/bin/pest tests/Feature/Scenarios/TestHelperUniquenessConformanceTest.php` — a path-scoped run loads only that path, and the gate names both files. The fix is usually to *reuse* the existing helper, not rename yours; shared ones belong in `tests/Pest.php` or a class under `Tests\Support`.
- **Business logic** goes in single-action services (`app/Services`); keep controllers + Filament pages thin.
- **Docs are part of "done":** changing a module's logic → update its `docs/modules/NN-*.md` (+ `docs/OVERVIEW.md` if cross-cutting) **in the same commit**.
- **Local DB:** MySQL; reseed with `php artisan migrate:fresh --seed` after a feature (`DemoSeeder` = canonical demo data). **`LearningSeeder` is the empty-mall variant** — the same reference data `atriom:install` lays down, one property, 12 vacant units, 3 tenants and *nothing else*, so an experiment's own numbers are the only numbers on screen.
- **Commits:** push to `main` directly (owner's established preference). End commit messages with the `Co-Authored-By:` line.

## Invariants — don't break
- **Money / AR:** `Invoice::recomputeTotals()` is the single source of truth — `paid_amount = captured payments + credit_applied_amount + applied tenant credit (`TenantCreditApplication`) + netted security deposit (`DepositApplication`)`, `balance = total − paid_amount`. Never set `paid_amount`/`balance` directly elsewhere. **FOUR channels, and every calculation that decides "how much of this invoice is settled" must count all four** — adding one means also updating `Invoice::capturedCashPaid()` (none of the three non-payment channels is cash, so the void guard must exclude them), the cancel-invoice release (or the settlement strands on an invoice that left the books), and BOTH payment over-allocation guards (`Payment::assertInvoicesNotOverAllocated()` and `refitAllocationsToBalance()` — omitting one lets a payment over-settle an invoice another channel already paid, burying the excess as negative AR; that has happened once already). **Item-level allocation (`invoice_item_payment`, MF-06) is NOT a fifth channel** — it records how an already-counted settlement splits across the lines. `App\Support\InvoiceItemSettlement` derives every per-line figure from `paid_amount`, so the item outstandings always sum back to `balance`; never store a per-item balance, that is a second truth about the same money.
- **An invoice's debtor is DERIVED on the form, and is NOT an invariant of the model.** The invoice form shows `tenant_id` read-only beside the lease picker and `CreateInvoice` re-derives it from the lease on save — a disabled field's value still arrives in the Livewire payload, so trusting it lets a crafted request bill a party who never agreed to the charge (until 2026-08-17 a free tenant picker made that two clicks in the UI). **Do NOT promote this to a model-level equality rule** — that was tried on 2026-08-17 and the full suite refused it, correctly: `IssueInvoiceService::issue()` takes an explicit `$tenantId` so a violation fine, a bounced-cheque fee and a late fee carry the debtor stated on their SOURCE document, and a DRAFT invoice may be freely re-homed to another lease before it is issued. Both are deliberate. The rule holds only on the one path where "the form never states a debtor" is unambiguously true.
- **General ledger:** `LedgerPoster::JOURNALIZERS` is the **single registry** of what posts to the GL; all four dispatch paths (real-time hooks · `accounting:sync-ledger` sweep · close gate · `billing:reconcile` drift check) **derive** from it via `LedgerPoster::sources()` — never re-list them. New money source = one registry line + its `LedgerRealtimeSync::SOURCE_DATE_COLUMNS` entry; `GlRegistryConformanceTest` fails CI otherwise. **A GL test that calls `LedgerPoster::post()`/`sync()` directly proves only the journalizer's arithmetic** — at least one test per source must drive the real service + the sweep and assert the tie-out. (This exact gap let applied SLA penalties cut a vendor bill while posting nothing — see [modules/21](docs/modules/21-general-ledger.md#gl-registry-gate).)
- **Tax** on service charges; **base rent is VAT-exempt**. **Marketing levy 5%** of base rent (that one IS a lease term, so it stays in settings — and is now actually editable there: it had no screen at all until 2026-08-12, so "configurable" was a claim only a deploy could honour). Two separate questions, two separate homes: **which supplies are taxable** is `charge_codes.tax_code` — the accountant's ruling, a row, no deploy (where Yardi puts it too) — and **what that tax charges** is the `tax_codes` + `tax_rates` catalogue at `/admin/tax-codes`. A rate is a **dated rung**, never a column: `Vat::rateForType($code, $on)` resolves for the DOCUMENT's date, so a rise can be entered in advance and a back-dated invoice keeps the rate that was in force. `TaxSettings::vat_standard_rate` is GONE (2026-08-12) — settings hold policy, master data holds rates. The catalogue is **the operator's own `account.tax` sheet** ([docs/accounting/EGYPTIAN-TAX-CATALOG.md](docs/accounting/EGYPTIAN-TAX-CATALOG.md)): VAT · stamp · schedule · withholding, each in both directions — **never invent a row beyond it, and never drop one** (`TaxCatalogueConformanceTest` gates both). **Stamp + schedule were COMMISSIONED 2026-08-19** and a fresh install ships them on (an existing DB gets the posting role backfilled and stays off — a reseed must never reactivate a code the operator retired). The blocker was never mainly the accounts: all three journalizers threw the document's own `tax_code` away — the invoice one summed every line's tax into one accumulator and credited `vat_payable`, the vendor-bill and expense ones hard-coded `vat_recoverable` — so an active stamp code would have put 20% of a supply on the VAT return, under the VAT liability, balanced and tied out. **Tax now groups by the tax code's own posting role**, exactly as revenue groups by the charge code's, with VAT as the floor for a document naming no code. The asymmetry is the real content and must not be flattened: output stamp/schedule are LIABILITIES, input stamp/schedule are **EXPENSES** (`stamp_tax_expense` / `schedule_tax_expense`), because neither has a credit mechanism the way input VAT does — copying the VAT shape there grows a receivable nobody can ever collect. `TaxCode` still refuses to activate a taxable code with no rate or no posting role, so an incomplete catalogue is inert rather than a trap. Activation grants nothing on its own: a code taxes a supply only when a CHARGE CODE points at it, which is the accountant's ruling and a row. **Every origination point calls `App\Support\Vat::rateForType($code, $on)`** (or `Vat::onType()`); a service calling `standardRate()`/`on()` directly can't see the ruling and fails `ExemptChargeTypesAgreeAcrossPathsTest`, and a literal rate anywhere fails `VatRateSettingTest`. `Vat::EXEMPT_TYPES` + `Vat::DEFAULT_STANDARD_RATE` are the FLOOR for an unseeded catalogue, not the policy — they must resolve identically to the seeded catalogue (`ChargeCodeVatTreatmentConformanceTest`), exactly as `InvoiceJournalizer::REVENUE_ROLE` floors the posting roles. Only **origination** reads any of it: an issued invoice keeps the rate it was billed at, so neither a rate change nor a treatment change ever rewrites history. **For a recurring charge, origination is BILLING, not the day the schedule row was written** — `charges.vat_rate` is an OVERRIDE and null is the normal state, with `Charge::resolvedVatRate($on)` the one place that answers what it bills on a date. Storing the catalogue's answer on the row is what broke this until 2026-08-12: the rate froze for the life of the lease, so a rise entered in advance reached every one-off charge and **never reached rent or service charge** — most of the money — and the amendment path carried the stale rate onto the new row too. Proven, not argued: with a rise to 20% effective 1 Sept, the resolver answered 20 for a September document while the September invoice billed 14. **`charges.vat_applicable` is an override on exactly the same terms, and that was the half nobody fixed until 2026-08-22 (EG-01)** — left `boolean default(true)` NOT NULL and written by thirteen services from `Vat::rateForType($type) > 0`, which is the WORSE half because `resolvedVatRate()` tests it FIRST and returns before the catalogue is consulted. A `base_rent` row is born `false` (rent is in `EXEMPT_TYPES`) and can never become taxable again: measured, with the charge code pointed at `VAT_14` the resolver answered 14.0, the charge resolved 0.0, the billing run raised a rent line with 0.00 VAT where 14,000 was due — and a rate the operator had deliberately TYPED was discarded too, because the short-circuit runs before the rate is read. Law 157/2025 makes that the exact change this operator is about to attempt. Now **nullable with null the normal state**, every row backfilled, and the test is `=== false` not falsy. **No screen ever offered it as a tick** — all three UI/import sites derived it — so nothing was preserved that anyone had stated; the operator's channel is the rate they type, and `vat_rate = 0` still holds a supply untaxed. An explicit `false` keeps its meaning and still wins over both. **Never copy the flag through a `(bool)` cast** — that turns null into false and re-freezes the row, which is what `TransferUnitOwnershipService` did to every resale. (`TaxabilityIsNotFrozenOntoAChargeRowTest`, `VatRiseReachesRecurringRentTest`.) **A document line records WHICH tax it carried** (`invoice_items.tax_code`, defaulted at the MODEL layer from the charge code so the eight line-raising services can't forget it) — a classification beside the rate, never a pointer the totals re-derive through. **The rate is picked, not typed**: read-only without `tax_codes.override` (withheld from `manager` — departing from the catalogue is an accounting act), enforced server-side by `App\Support\CatalogueTaxRate` from the items repeater's `mutateRelationshipData…Using` hooks. **That layer is load-bearing** — the repeater is relationship-backed, so rows never reach the page's `mutateFormDataBeforeCreate` and a guard written there protects nothing.
- **Money records are NEVER deletable — not even by super_admin** (operator decision 2026-07-31). Invoice, Payment, JournalEntry, CreditNote, VendorBill, Expense, DepositTransaction, Payroll, PostDatedCheque: no Delete/ForceDelete action, no `{module}.delete` permission, and a model-level refusal (`RefusesDeletionOfCommittedRecords`) as the backstop. Correct them through their own workflow — cancel / void / credit note / reverse — which leaves a document an auditor can follow. An UNCOMMITTED record is still removable (a draft journal entry, a payment that never became money), which is what keeps `CreatePayment`'s orphan rollback working. Registry = `App\Support\DeletionPolicy`, which **derives** the tiers from an attribute on each model (2026-08-15) — you classify a model by writing `#[NeverDeletable(correction: …)]` / `#[DeletableWhenUnused(blockedBy: […], instead: …)]` / `#[DeletionAllowed(reason: …)]` on the class, not by editing an array; `DeletionPolicyConformanceTest` fails the build if a Delete button or permission reappears. **Master data with history is refused too** (`#[DeletableWhenUnused]` — Tenant, Vendor, Lease, Unit, Asset, Employee): deletable only while nothing references it, otherwise deactivate. This follows Yardi/MRI/Entrata, which all refuse rather than warn — the damage lands on the reports and audit trail that referenced the record, not on the record itself. `blocked_by` relations are verified to EXIST by the gate (a typo'd relation blocks nothing and looks identical to a working guard). Note `Unit` uses `allLeases` (the pivot), not `leases`. **Every model is classified** — `#[NeverDeletable]` / `#[DeletableWhenUnused]` / `#[DeletionAllowed]` (with a stated reason) — and the gate fails on an unclassified one, because it discovers models by globbing `app/Models` rather than by reading the registry, so a new model forces a decision rather than inheriting a default. Before adding `#[NeverDeletable]`, check for a real deletion call site in `app/`: guarding a row a service legitimately deletes breaks the workflow instead of protecting it (that check saved the credit-note un-apply, the tenant-credit reversal, the owner-statement rebuild, and the advance-repayment reversal). Two models are deliberately `#[DeletionAllowed]` despite carrying history — `UtilityMeter` and `FixedAsset` — because soft-delete IS their tested retirement path and the GL/trend already handle it; both omissions are annotated in the registry. **Everything else: delete = super_admin only**; bulk-delete is off project-wide (opt-in via `$bulkDeletable`). CRUD gating via `RoleGatedActions` on `{module}.{action}` permissions (`RolesPermissionsSeeder`).
- **Property isolation:** every module is isolated to the selected property. **Reads:** resource tables auto-scope; scope any cross-property Filament select via `App\Support\TenantScope::selectable*` / `visibleAssetIds()` (never `currentAssetId()` alone — null in All-mode leaks); "All Properties" pseudo-asset = `Asset::ALL_PROPERTIES_CODE`. **Writes:** if a form exposes/derives an editable `asset_id`, guard it with `GuardsAssetInScope::assertAssetInScope()` on create+edit (Filament only stamps `asset_id` on create, never update). Shared-vs-isolated register = `App\Support\PropertyIsolation`; the `PropertyIsolationConformanceTest` gate fails CI if a new model/resource ships unclassified/unscoped/unguarded. **The property field itself is `App\Support\Filament\PropertyField::make()`, never a bare `EntitySelect::make('asset_id')`** — with a real mall selected `visibleAssetIds()` is `[currentId]`, so a blank property is a bare **403** from `assertAssetInScope((int) null === 0)` and a foreign one fails `EntitySelect`'s label lookup at validation. Both refusals were already airtight; what 7 screens did was OFFER those options anyway, so "Consolidated (all)" on a filled-in journal entry ended at a 403 wall and the six financial statements ran under a *"Consolidated (all)"* caption while `TenantScope::reportAssetIds()` clamped every pick back to the selected mall — right figures, wrong caption, which nobody re-checks. The component pins + disables + **dehydrates** (a disabled input is not submitted, so without it the pinned value never reaches the model); pass an extra lock as `$alsoDisabledWhen`, because chaining `->disabled()` after it silently unpins the field. `PropertyField::free()` is the opt-out for the four PORTFOLIO-CONFIG screens in `PropertyField::PORTFOLIO_LEVEL` (posting map · departments · **holidays** · owner requests), each with a reason — and for the two whose null means EVERY mall rather than no mall (departments, holidays) the write guard is `GuardsPortfolioWideRows`, which checks both ends of a move and requires the actor to hold every property. **The pin is a UI truth, not a gate** — the value still arrives in the Livewire payload, so every `assertAssetInScope()` stays. `PropertyFieldPinnedConformanceTest` RENDERS each create form and reads the built component's state (a call site can chain `->disabled(false)` and look correct in source), and fails on a stale exemption. **Read [docs/PROPERTY-ISOLATION.md](docs/PROPERTY-ISOLATION.md) before adding a property-owned module.**
- **You cannot grant access you do not hold.** `users.create`/`users.edit` are held by `manager`, `hr` and `mall_admin` as well as super_admin, and the user form's property-assignment field is what grants access to a mall — so until 2026-08-17 a manager pinned to Mall A could open their OWN record, add Mall B and see it. Privilege escalation through an ordinary CRUD screen, demonstrated through the real form. `UserResource::enforceGrantableAssetsRule()` reverts BOTH directions (a restricted grantor can neither grant nor REVOKE a property they cannot see) and logs the attempt to `AccessControlAudit` — mirroring `enforceProtectedRolesRule()`, which this screen already used for the same class of problem. It runs in `afterCreate`/`afterSave`, not in a `mutateFormData…` hook, because a relationship Select saves from COMPONENT STATE via `saveRelationships()` and never reads mutated form data. Measured against `AssignedAssets::idsForCurrentUser()`, NOT `TenantScope::visibleAssetIds()` — the latter collapses to the SELECTED property, which would stop an hr user holding two malls granting the one they are not looking at. The picker itself stays portfolio-wide (`->acrossProperties()`): a narrowed option list is not a gate, since the assignment arrives as a Livewire payload.
- **Auth surfaces:** `/admin` = `User` + spatie roles · `/portal` = `TenantUser` (multi-user; only `is_admin` may write) · `/api/v1` = Sanctum `tenant-api` against `Tenant`. Cross-tenant API returns **404** (no existence enumeration).
- **A draft is not a document — the tenant never sees one.** "Whose row is this?" and "has this been raised?" are **two questions**, and scoping through `$request->user()->invoices()` only answers the first. Every tenant-facing read must also narrow with `->visibleToTenant()` (`App\Support\TenantVisibility` + the `HidesDraftsFromTenant` concern); the relationship itself must NOT be narrowed, because admin and the GL read the same one and need every row. `invoices.status` and `credit_notes.status` both **DEFAULT to `'draft'` at the column**, so a draft is what any create that omits the status produces (`CreditUnearnedBillingService` does) — this is the normal case, not an exotic one. It leaked on **seven surfaces at once** (list · show · invoice PDF · Statement of Account · `pay-demo` · `paymob-session` · the portal invoice table), and `?status=draft` let a tenant enumerate them. The **visible** set is derived — `ValueSets::allowed()` minus `HIDDEN` — so a new status is visible by default and must be hidden deliberately; the scope **excludes** rather than allowlists, so a legacy/imported status still reaches its tenant (losing a real document from someone's history is the worse failure). Only `draft` is hidden: a `cancelled` or `written_off` invoice still explains a number the tenant remembers. **The portal and `/api/v1` are the same surface with different renderers** — fix both or neither. `TenantNeverSeesADraftTest` pairs every refusal with a control that must succeed, because a scope that hid everything would satisfy the refusals alone and read as a pass.
- **`visible()` is NOT an authorization gate.** (`ActionAuthzConformanceTest` now gates this: every `Action::make()` chain under `app/Filament` carrying an `->action()` must also carry `->authorize()`/`abort_unless`, or be registered in `App\Support\ActionAuthz::EXEMPT` with a reason.) **Correction 2026-07-31 — the "still dispatchable" half of this was WRONG on the version we ship.** `mountAction()` does check `isDisabled()`, and `CanBeDisabled::isDisabled()` returns true when `isHidden()` does (`vendor/filament/actions/src/Concerns/CanBeDisabled.php:24`), so on **Filament v4.11.8 a `visible()`-only action IS refused at dispatch**. Found by mutation-testing the module-08 fix: deleting CAM's `abort_unless` left `CamActionAuthzTest` fully green — those tests never exercised the gate they describe. **The second layer is now real, and global (2026-08-12).** `Action::make()` resolves through the container, so `Filament\Actions\Action` is bound to `App\Support\Filament\AuthorizedAction`, which runs `abort_unless($this->isAuthorized(), 403)` inside `call()` — the check Filament's own `Action::call()` never performed. That closes FS-23 at one seam instead of in 76 files: `->authorize()` folds into `isHidden()` folds into `isDisabled()`, so on the letter of it `visible()` and `->authorize()` were one layer, and the 76 write actions gating with `->authorize()` alone (journal-entry post/void, void_invoice, period close) had no second one. `isAuthorized()` returns true when nothing was declared, so the ~500 actions gating with `abort_unless` are untouched. `ActionCallIsAuthorizedTest` pins the refusal AND the binding, so a Filament release switching `make()` to `new static` turns the build red rather than quietly removing the layer. **Double-gate anyway**, for a reason that survives the correction: `->authorize()` is a stated intent, while hidden-implies-disabled is an upstream implementation detail that can change in a release and would silently reopen every `visible()`-only write at once. `FilamentActionDispatchContractTest` pins that upstream behaviour so an upgrade that changes it turns the build red; `ActionAuthzConformanceTest` enforces the layer we control. Every write action must gate in **both** `visible()` (the UI) and `action()` (`abort_unless(...)` — the actual gate); name the predicate once so they can't drift. **In tests, neither `->callAction()` NOR `mountAction` proves the `action()` gate** — `callAction()` asserts visibility first, and `mountAction` refuses hidden actions for the reason above, so both go green whether or not the gate exists. To prove a gate, remove it and watch the test fail; to test one, assert the predicate directly. And always pair a refusal test with an authorised control — a refusal passes just as happily when the dispatch is a no-op.
- **A screen is SEVERAL Livewire components, and a success toast is not a refreshed screen.** A record page, each relation manager under it and each header widget are separate components with separate lifecycles; Livewire 3 re-renders only the one that handled the click (the widgets blade mounts each with a STABLE `key()`, which is exactly what tells Livewire to leave a child alone). Two seams fix the two halves. **(a) `refreshFormData()` never re-reads.** It refills from `$this->getRecord()->attributesToArray()` — the page's IN-MEMORY copy — so behind any service that re-reads its subject as a locking read into a new instance, which is what EVERY money service here does and must do, the call refills the same stale values and does nothing. Proven, not argued: `EditInvoice::void_invoice` left the form reading `issued` / `10,000.00` while the row read `cancelled` / `0.00`, with `refreshFormData(['status','balance','notes'])` sitting in the action. **Nineteen call sites across eight money pages had that shape — one of them, the payroll-lines listener, re-read first and was the only correct one — and the suite was green throughout, because every test asserted `$invoice->fresh()->status` — the ROW — and none asserted the form.** `App\Support\Filament\RefreshesRecordState` re-reads before refilling; use it on any Edit/View page that refills, and `RecordStateRefreshConformanceTest` fails the build otherwise. **(b) nothing tells the rest of the screen.** `App\Support\Filament\RecordChanged::EVENT` is the ONE event (deliberately not per-module — a second name is a second thing to forget), announced automatically after every action: `Action::make()` resolves to `AuthorizedAction`, and `CreateAction`/`EditAction`/`DeleteAction` resolve to the three `Announcing*Action` bindings, because those are subclasses and never saw the `Action` binding. A widget opts in with `RefreshesOnRecordChange` (an empty listener IS the refresh — Livewire re-renders for any listener call). **A download announces nothing** — the seam tests the action's RETURN VALUE for a `Response` rather than keeping a list of read-only action names.

- **Changing a posted document:** the ledger here is **derived, not journalled** — `LedgerPoster::sync()` re-reads a document and, when its posted entry no longer matches, **voids it and posts a fresh one**. So "may this edit move the books?" is a decision, and every fillable column of every GL source declares it in `App\Support\ChangeImpact::POLICY`: **REFUSED** (immutable once committed — correct via a new document) · **DERIVED** (entry is void-and-reposted) · **PROSPECTIVE** (future documents only) · **DESCRIPTIVE** (reaches the entry's description but never re-derives, because `matches()` compares lines + date + asset and not text) · **NEUTRAL**. The governing rule: **a change may re-derive a posted entry only while that entry is not yet evidence** — filed with ETA, delivered to the counterparty, inside a closed period, or inside an issued owner statement. `ChangeImpactConformanceTest` fails the build on an unclassified field, on a classified column that no longer exists, on a field a journalizer reads being called neutral, on a posting-date column classified neutral — and **proves every REFUSED field by dirtying it on a committed fixture** rather than asserting a guard exists. A source declaring refusals must add that fixture. See [docs/accounting/CHANGE-IMPACT-PLAN.md](docs/accounting/CHANGE-IMPACT-PLAN.md).
- **Posting dates:** any date that becomes a journal entry's `entry_date` must be refused when its period is **closed** — otherwise the row commits, the operator sees "Saved ✓", and the entry is refused inside the best-effort sync job that only logs. Every GL source declares its guard **on the model** (2026-08-15) — `#[PostingDateGuardedBy(guard: SomeService::class)]`, or `#[PostingDateNotOperatorTyped(reason: …)]` when the date can never be operator-typed; `App\Support\PostingDateGuards::guards()` derives the register and `PostingDateGuardConformanceTest` fails if a new source ships unclassified. **Read `PostingDateNotOperatorTyped`'s docblock before claiming that exemption** — one asserting a safety property that does not hold is worse than no entry at all, because the gate then reports coverage it does not have (that is how a back-dated settlement netted 120,000 into a closed March). Guard in the **service**; use the `GuardsPostingDate` model trait only where there is no create/update service. A **MISSING** period is allowed — only a CLOSED one is refused. *(This exact bug was fixed six times, one module at a time, before the gate existed.)*
- **A `DomainException` is a refusal, not a fault** — it renders as a message + redirect-back (`bootstrap/app.php`), never the 500 page. Filament then reads that page GET as a component update, asks `PersistentMiddleware::makeFakeRequest()` for a request that doesn't exist, and the page **405s**. `IgnoreStrayLivewireHeader` (global, prepended) strips the header off safe-method app routes so the refusal renders as its toast. - **A class you name must be one you imported.** An unimported name is valid PHP — it autoloads, `php -l` passes, and `::class` is just a string — so `app(ExerciseLeaseOptionService::class)` inside `App\Filament\Admin\Actions` silently asked the container for `App\Filament\Admin\Actions\ExerciseLeaseOptionService` and 500'd the Renew modal (2026-08-17). **Class names do NOT fall back to the global namespace** (functions and constants do), which is why a bare `DB::table()` in the same file was a second, unreported crash waiting on a different button — and why a resolver that tries the global name as a fallback finds Laravel's `DB`/`Str`/`Log` aliases and reports the bug as fine. `UnresolvedClassReferenceConformanceTest` resolves every reference under `app/` the way PHP would; add the `use`, never fully-qualify inline. **It reads FOUR forms, and the fourth was added 2026-08-20 after two live 500s it could not see**: `Foo::`, `new Foo`, `instanceof Foo`, and a **TYPE DECLARATION** — `fn (Foo $x)`, `private Foo $y`, `catch (Foo $e)`. A type hint fails at CALL time in exactly the closures the `::` form fails in, and reads identically in review. It had shipped twice: `UtilityMetersTable` typed three closure params `UtilityMeter` with no import (the whole meters LIST 500'd, in `4f58ce8c`), and `VendorForm` typed one `?Vendor` (the vendor EDIT form 500'd — and `ResourceFormSmokeTest` mounts CREATE pages only, where `?Vendor $record` is legitimately null, so nothing caught it). The trap when extending it: a ternary's `?` sits between the name and the variable (`$a->notes ? $b : $c`) exactly where a nullable type's `?` does NOT, so reading `?` as a type marker in the leading position reports every such ternary as a missing import — the run must START at a name. Both references sat in **closures** (`fillForm`, `schema`), which run only when an operator opens the modal — so a test that enumerates actions and asserts their shape passes while every one of them is broken. **Build an action in a test and you have tested nothing; `mount()` is the seam Filament calls on open.** The same shape a day earlier, in a FORM rather than an action: `InvoiceForm::prefillItemsFromLease()` had a closure missing `use ($get)` — an `Undefined variable` on PHP 8 — which 500'd the first click of raising an invoice for five days, because every test of that behaviour called the SERVICE. - **Turning a module off stops its scheduled work, and the guard is ONE seam** (2026-08-21). `Modules::enabled()` gated navigation, resources and actions — and exactly ONE of 34 scheduled commands. `App\Support\ScheduledModules::guard()` now attaches the skip to every event from one registry, applied once at the END of `routes/console.php` after everything is defined; a `->skip()` per command is 33 chances to forget and the next command inherits nothing. Every scheduled command is classified `OWNED_BY` a module or `CORE` **with the reason it can never be switched off**. **A key outside `Modules::KEYS` is a guard that can never refuse** — `enabled()` returns TRUE for anything unlisted, deliberately, so core features need no entry; that makes a typo'd or aspirational key silent. `Modules::enabled('billing')` was one, and the first draft of the new registry contained another (`marketing`), so `ScheduledModuleGateConformanceTest` sweeps EVERY such literal under `app/`, not just the registry.
- **UNFINISHED work is FROZEN in code, not left as a toggle — and ETA (module 16) is the one** (2026-08-22). `Modules::FROZEN` is the registry; `Modules::enabled()` answers **false before the settings row is consulted**, so a stale row, a restored backup or a hand-edited `settings` table cannot bring an uncertified integration back. **`modules.eta` had already defaulted to false since 2026-07-03 and ETA was still everywhere an operator looks** — that is the whole lesson. A settings tab with two `->required()` fields nothing read; a Modules toggle *inviting* them to switch it on; an **"ETA Status" column on every invoice list**, the one surface never module-gated; *"Submit invoices to the Egyptian Tax Authority"* as a grantable right on the roles matrix; an ETA block on the invoice PDF printing a **mock** submission id onto the document a tenant files with their own accountant; three `eta_*` keys in the mobile API payload; and ~55 seeded "Valid" badges in the demo data, which is what makes an unfinished module read as a finished one. **Off and unfinished looked identical, and the difference was presented as the operator's decision.** It is not. **The key STAYS in `Modules::KEYS`** — a key outside it is a guard that can never refuse, so removing `eta` would turn every call site into a permanent *yes*, silently. The Settings screen builds its toggles from **`Modules::toggleable()`**, never `KEYS`, and `SettingsPageConformanceTest` exempts a frozen module's flag from "every setting needs a field" **derived from the registry**, not by name. **Freezing DELETES what only existed to serve it**: `EtaSettings` (all four properties inert — the pipeline reads `config('eta.*')` from env, and `TaxSettings` is the surviving home for the issuer identity), the `invoices.submit_to_eta` permission (the roles matrix renders a checkbox per catalogue row, and the seeder only ever ADDS — so retiring one needs a migration), `DemoSeeder::seedEtaSubmissions()`, the landing page's claims, and the settings/notification lang keys. **It KEEPS the code and its service-level tests** — `app/Services/Eta/*`, the job, `config/eta.php`, the columns, the widget's registration — because those tests never ask `Modules::enabled()` and are what make resuming cheap; only the two UI suites are `->skip()`ed with the reason. **One exception to "gate, don't delete": the mobile API.** `docs/api/openapi.json` is GENERATED from `InvoiceResource::toArray()`, and both gated forms corrupt it — a conditional spread becomes a property with an EMPTY NAME inside an `anyOf`, a post-return `if` becomes three *required* keys the endpoint never sends. A generated spec has to describe what the endpoint returns, so the three `eta_*` keys are removed outright and re-adding them is on the unfreeze checklist. Unfreeze = delete the entry, restore the permission line and re-run the seeder, re-add the API keys and `composer api-spec`, point `EtaJsonBuilder`'s issuer at `TaxSettings`, drop the `->skip()`s; `EtaIsFrozenAndInvisibleTest` will go red, and **that is the signal the freeze lifted, not a regression**. Every refusal in it is paired with a control AND flips the settings row ON first — otherwise it passes for the old reason (the default) and would stay green with the freeze deleted.
- **A per-property setting the SCHEDULER cannot honour is not a setting** (2026-08-21). `billing.monthly_billing_day` became a `PropertySettings::OVERRIDABLE` key, and there is ONE scheduler for the portfolio — so `->monthlyOn($globalDay)` would have let an operator set Mall B to the 25th, see it saved, and still bill on the 1st. Both money runs fire **daily** and ask `App\Support\BillingDay` whose day it is; the rule lives in one class because it was copy-pasted into two and two copies of *when money is billed* can drift onto different days. **Clamp to the month's last day** — a property set to the 31st otherwise skips seven months of the year, silently, since nothing reports a run that did not happen. And key the sweep on an EXPLICIT flag, never on "was a period given": inferring it made `billing:run-monthly --queue` — the catch-up after a failed billing night — a no-op on 29 days in 30 while printing "job dispatched".
- **Scheduled scans** must be idempotent + lock-safe (`lockForUpdate` + re-check the stamp inside the transaction).
- **A stored column that is a function of TODAY needs a SCHEDULED sweep, and the registry is `App\Support\ProjectedState`.** Two are: `units.status` (derived from the leases currently holding the unit) and `leases.status` (should stop being `active` once the term has run out). Both are stored because every list, filter, map and occupancy figure reads them — and both go wrong **on a day when nothing happened**, which no write-triggered recomputation can ever catch. `Unit::recomputeStatus()` existed and was correct for the whole of module 01's life; it just never ran on a timer, so a give-back effective 1 January recorded in August left the column saying `occupied` from January onward. Nothing moved a lease to `expired` at all: measured seven months after a term ended, the lease read `active`, the unit read `occupied`, the shop was **un-relettable** (`LeaseCreationService` refused with "this unit already has an active lease") and `RentEscalationService` was still stepping its rent. `leases:expire` does both, in that order. `Lease::hasExpiredTerm()` is the ONE definition of "the term has run out", shared by the sweep and by the escalation guard so they cannot drift; a converted holdover is excluded, because its expiry is deliberately in the past. The gate has four teeth — projector exists, sweep exists, sweep is **scheduled** (an unscheduled one is the original bug exactly), and a second consecutive run finds no work — and `NOT_PROJECTED` records, with reasons, the four columns that look like projections and are not.
- **A GATE CAN REPORT ON A SET IT HAS SILENTLY STOPPED COLLECTING** (third instance, 2026-08-21). `TestHelperUniquenessConformanceTest` tracks brace depth to tell a file-scope `function` from a method — and PHP's tokenizer emits `T_CURLY_OPEN` (an ARRAY token) for `"{$x}"` but a **plain** `}` for its close, so every interpolated string decremented the counter without incrementing it. A file with a few of them sat at negative depth for the rest of the scan and no file-scope function in it was ever recorded. `tests/Pest.php` is full of interpolation, so the one file this guide tells you to put shared helpers in was exactly the one the gate could not see: a helper declared there AND in a test file exited the suite 255 with zero bytes on both streams while the gate stayed green. Same class as the reconciliation check that could not fail and the sweep that matched zero models — and the tell was never the gate, it was the symptom the gate's own docblock says it exists to prevent. **When a gate counts, assert it counted something.**
- **A reconciliation check must be ABLE to fail.** `billing:reconcile`'s CAM tie-out asserted `Σ allocated + landlord_unrecovered == total_actual_expense` while the generator WRITES `landlord_unrecovered = actual − Σ allocated` — so the identity held by construction whatever the shares summed to, and a pool recovering **1,150,000 against 1,000,000 of actual common cost** passed it cleanly. It was not wrong about anything; it could not be wrong about anything. Reading a check tells you what it compares, only MUTATION tells you what it notices: `ReconciliationChecksCanFailConformanceTest` perturbs each of the four tenant-facing checks (balance · paid_amount · cam_allocations · deposits_tie_out) and requires it to go red, **paired with a control requiring all four green on clean data** — a check that fails on everything is no better than one that fails on nothing. Adding a check means adding its mutation. The GL tie-outs are deliberately out of scope and said so, rather than implied.
- **A lock serialises writers; it does NOT make the guard behind it see them.** Under MySQL REPEATABLE READ a transaction's consistent-read snapshot is fixed at its FIRST plain read, so a guard that runs *after* `lockForUpdate()` is still answered from before the wait. Proven with two processes on two connections (2026-08-19): the second transaction's `isActivelyLeased()` returned **false** with the first transaction's lease committed on that very unit, while a **locking** read of the same query at the same instant returned 1. `LeaseCreationService` and `Payment::assertInvoicesNotOverAllocated()` both had this shape, and what actually prevented the double-booking was the UNIQUE index on the document number — which only worked because both writers computed the SAME number from the same stale snapshot, so the loser got a duplicate-key **500** instead of the intended refusal. Every guard query behind a lock must itself be a locking read (`Unit::isActivelyLeasedForUpdate()`, and all four settlement-channel sums). **The suite cannot catch this** — SQLite compiles locks to nothing and one connection never interleaves; the proof is `docs/qa/scripts/race.sh`, run against MySQL.
- **Concurrency: every lock is registered, and the registry has teeth.** `SQLiteGrammar::compileLock()` returns `''` and the suite runs on sqlite `:memory:`, so **every one of the registered lock acquisitions (`ConcurrencyPolicy::totalLocks()`, 134 today) is inert in every test** — deleting one used to turn nothing red, in the one invariant class this project has actually been bitten by twice (the unit double-booking, the Paymob double-charge). `App\Support\ConcurrencyPolicy` registers every file that takes a row lock (`lockForUpdate`/`sharedLock`) **or an atomic cache lock** (`Cache::lock` — same guard, different mechanism, used where the thing protected is a sequence rather than a row), **with its lock count**; `ConcurrencyPolicyConformanceTest` fails on an unregistered file, on a registered file that stops locking, and on count drift — so one lock dropped from `CreditNoteService`'s eleven is visible. The `PROVEN` tier goes further: `Tests\Support\LockSpy` swaps in a grammar that compiles the lock to a **SQL comment** (valid SQLite, behaviour-neutral), so `DB::listen()` can see which table a service actually locked on the real path — those tests fail when the lock is removed. **A lock on the right table is not proof the service under test took it**: with auto-apply-credit on, the late-fee test passed with its own lock deleted because another service locked `invoices` in the same request. Isolate, then mutate. **A registered file is not a guarded decision.** `AUTHORITATIVE_GUARDS` names the three methods whose REFUSAL rests on what they read under a lock — `Unit::isActivelyLeasedForUpdate`, and both payment over-allocation guards — and the gate reads each one's own method body and requires a locking read in it. That is a different property from "this file locks somewhere": on MySQL's REPEATABLE READ a plain `select` inside a transaction answers from the snapshot taken at its start, so a guard that locks the row and then re-reads its dependants without `lockForUpdate()` decides on stale data while looking correct — and on sqlite it looks correct too, because nothing compiles. None of this proves two transactions serialise — that needs MySQL and two connections, which is now `tests/Mysql/` (it SKIPS unless the connection really is MySQL, so the ordinary run is unchanged).
- **Every service must be REACHABLE, and a green test is not reachability.** Every other gate here checks that a thing is *classified*; none checked that a thing can be *started*. A sweep on 2026-08-18 traced every class in `app/Services` to an entry point and found **four with none** — `BillUnitOwnershipsService` (the monthly صيانة run: no command, no job, no schedule, no button, so **every unit owner went un-billed in production** while its own docblock spoke of "the scheduled one"), `TransferUnitOwnershipService` (a unit could be resold and there was no way to record it), `AssetStatementPdfService` (orphaned when the `/owner` panel took its button with it), and `VendorScorecardService` (built with seven regression tests and no screen, sitting in `docs/ROADMAP.md` as work to do while the work was done). All four were fully built, fully tested and unusable — **the tests are what hid them**, because a service with a green test file looks maintained and `grep` says it is referenced. `App\Support\ServiceReachability` seeds from the layers a person or a schedule can actually start (Filament · console · jobs · HTTP · listeners · observers · models · providers · routes) and takes the **transitive closure** — a service called only by other services is fine when one of them is reachable, but a cluster that only calls itself is an orphaned island, which a rule of "referenced by any service" would wave through. **`tests/` and `database/` are deliberately NOT seeds** (proven by mutation: a probe service with a passing test is still flagged). `ServiceReachabilityConformanceTest` fails on an unreachable service, on a stale `EXEMPT` entry, and on an exemption whose reason is too thin to review — "will be used later" is exactly what the scorecard's backlog entry said for a month. **Reachable is not the same as configurable.** `ServiceReachability` proves a service can be STARTED; it says nothing about whether the data it needs can be CREATED, and that gap billed nobody for module 37's entire life — `BillUnitOwnershipsService` was scheduled and reachable, and no screen or importer could give an ownership the schedule it bills from, so every handed-over owner was reported as an unremarkable `skipped`. `BillableAgreementIsConfigurableConformanceTest` closes the other half: for every `BillableAgreement` there must be a charges relation manager AND an importer column, so a new agreement type cannot ship with one road open and the other closed. **And a PERMISSION must be checked somewhere** (`App\Support\PermissionReach`, 2026-08-19) — the third class from that sweep. It fails in the confusing direction: the role appears to hold the right, the screen refuses, and nobody can tell policy from bug (`requests.change_status` was granted to `technician` while the action gated on `canEdit()`, so that role's whole function was dead). Reachability is DERIVED three ways because most keys are never written down — `hasPermission($action)` composes `"{$module}.{$action}"` at runtime, so a literal grep reports ~100 phantom misses: a literal in `app/`, a dynamic key attributed **by directory** to its own module (crediting every module with every action anyone calls is the loosening that makes the gate meaningless), or `AssignmentScope`'s `view_all`. It found one live drift — the activity log gated on an inline role list while `activity_log.view` was checked nowhere, so `mall_admin` held the right and was refused — and one standing decision: **all 41 `{module}.delete` keys grant nothing**, because `canDelete()` checks the role and never the permission. They are classified, not removed; either honour them or drop them, but a permission that reads as a right and grants nothing should not continue.
- **Every screen explains itself, in both languages.** `App\Support\ScreenGuides::SCREENS` maps all **99 screens** (56 admin resources · 32 admin pages · 11 portal resources) to a four-field guide in `lang/{en,ar}/guides.php` — *purpose · steps · affects · rules*. `affects` is the field that earns the panel: what moves ELSEWHERE when you touch this screen is the one thing nothing else in the app tells anyone. The panel mounts as `GuideAction::for(static::getResource())` on a resource's List page and `GuideAction::for(static::class)` on a page. `ScreenGuideConformanceTest` discovers every screen class on disk and fails on one that is neither registered nor `EXEMPT` with a reason — **and separately checks it is MOUNTED**, because a written guide nobody can open helps nobody. `EXEMPT` is empty and the gate rejects a stale entry: the login and tenancy-registration screens extend `SimplePage`, not `Page`, so discovery never offers them. The portal has its own `portal_*` namespace — a guide telling a tenant what the billing run does answers a question they cannot act on.
- **Field help is sorted by what it DOES, not stacked under the field.** Three homes: `helperText` (always visible) carries only what changes what you type — a constraint, a derivation, a consequence, or live feedback computed at runtime; `->hintIcon(Heroicon::OutlinedQuestionMarkCircle, __('admin.hints.X'))` carries the WHY, one hover away with a visible affordance; the screen guide carries what is really about the module. Budget is **18 words** (`App\Support\FieldHelp::WORD_BUDGET`) — twelve turned good one-liners into fragments. `FieldHelpConformanceTest` gates the budget (exemptions carry a reason in `LONG_BY_DESIGN`), a hint icon with no tooltip, a hint written-but-never-shown OR shown-but-never-written, and an exemption whose string is already short. **Tooltips are not a substitute for a visible constraint** — hover vanishes on touch, and a first-time operator cannot see the rule that would have stopped them. Check the CALL SITE before shortening: a string already rendered as a `->tooltip()` or `->modalDescription()` is already one hover away, and one reporting record STATE is live feedback, not explanation.

Output goes to `storage/app/handbook` — **outside the webroot on purpose**, so nginx cannot serve it and the `auth` on `/handbook` genuinely applies; missing, it answers **503 naming the missing step**. EN at `/`, AR at `/ar/`, **26 pages per locale at parity**. - **PM compliance is DERIVED, never stored** (2026-08-20). `FacilityWorkOrder::pmComplianceState()` answers `on_time` · `late` · `overdue` · `due` from two columns that existed all along — `scheduled_for` **is** the plan's due date, because the generator copies `next_due_date` onto the order — and returns null for a corrective job (it answers to its SLA) or a cancelled cycle. `overdue` is a function of TODAY, so storing it would need a sweep and would go wrong on a day when nothing happened. **Completing at 16:00 on the due day is ON TIME**: compare whole days, or a datetime-vs-date comparison calls every afternoon completion late. - **A trade is a ROW, and it is the spine of the facility model.** `App\Models\Trade` (2026-08-20) classifies work orders, service plans AND equipment; `vendor->trades()` says who may be dispatched to it; `standard_hourly_rate` is the craft rate the work-order cost object reads. It replaced `category` — a `Select` fed from `__('admin.facility.categories')`, i.e. a **translation array**: not in `ValueSets` so the column was unenforced, un-extendable without a deploy in two languages, and hardcoded a second and third time in `EquipmentForm`/`EquipmentTable` with four trades missing from both. **Never re-introduce `category` on those three tables** — two columns answering "what kind of work is this" is two truths about one question. **A tenant picks a PROBLEM, not a trade**: `tenant_requests.category` is a subcategory of its `TenantRequestType` and only the *Maintenance* type's subcategories map to trades, so `RaiseCorrectiveWorkOrderService::tradeForRequest()` RESOLVES it and yields null for a noise complaint — copying it across is what put `noise`/`parking`/`lease_copy` in the trade column for the whole of module 26's life. **Since EG-14 the resolution is a FOREIGN KEY, not a name match** (`tenant_request_subcategories.trade_id`): comparing `category` against `trades.code` was a bridge between two lists nothing kept in step — seven subcategories against fourteen trades — so a tenant could not report a stuck lift, a generator failure, a fire-safety fault, a pest problem, a security issue, a landscaping fault or a waste problem, and every work order raised from those arrived with NO trade. The link also survives a code mismatch the match could not: `fire_safety` → `fire-safety`. **The TYPE stays a PHP enum** — it carries behaviour, and rows would let an operator create a type the code has no answers for; only the vocabulary is a catalogue. **Eligibility is a suggestion, compliance is the gate**: `Vendor::assignableOptions()` GROUPS the picker ("Does this trade" / "Other vendors") and never filters, because Filament validates a Select with `Rule::in` and refusing an unusual-but-legitimate pick is the worse failure; `Vendor::isDispatchable()` stays the only hard block. The yardstick is [docs/benchmarks/fm/](docs/benchmarks/fm/) — **IBM Maximo** for the work-and-asset core, **ServiceChannel** for the contractor loop.

That is how the trade and failure-code registers shipped invisible for a day in August 2026. Same class as `atriom:rebuild-search`: a change to a seeder is a DEPLOY step, and `FacilityScreensAllRenderTest` now asserts every facility screen's permission actually exists and that a manager holds it.

**"Maintenance" is not an identifier in this system (2026-08-15).** The word meant five different things and only two of them were ever the same module, so it is now reserved for the four places it is plain English rather than a name:
- `units.status = 'maintenance'` — a unit out of service ("Under Maintenance")
- the `maintenance` expense / vendor-bill category — posts to `maintenance_expense`
- `TenantRequestType::Maintenance` — a maintenance request is one KIND of tenant request
- Laravel's own maintenance mode (`php artisan down`)

Everything else moved. Module 11 (tenant requests) → `requests.*` permissions, `Modules::enabled('requests')`, `config/requests.php`. Module 26 (facility) → `facility.*` permissions, `Modules::enabled('facility')`, models `FacilityWorkOrder` / `FacilityWorkOrderItem` / `FacilityWorkOrderPart` / `ServicePlan` / `SlaPenalty` over `facility_work_orders` / `service_plans` / `sla_penalties`. The SLA hours both modules read are `SlaSettings` (group `sla`) + `config/sla.php` — named for neither module on purpose, because naming shared settings after one consumer is what created the confusion in the first place. **A shared setting has to be honoured by every consumer or it means two things** (2026-08-21): `sla_working_clock_priorities` lists the priorities measured on `App\Support\WorkingCalendar` — Egypt's Fri–Sat weekend, the operator's `holidays` register and Ramadan short days, resolved per property — and it shipped honoured by module 26 and silently ignored by module 11, so ticking `medium` gave a work order and a tenant request different deadlines. Both now read `SlaResolver::clockFor()` for the CANONICAL clock names (neither module owns that vocabulary) and both **freeze** the answer on the row — `facility_work_orders.sla_clock` and `tenant_requests.sla_clock` — because a pending SLA is re-read on every breach scan, so resolving at read time would re-time every running job the moment the setting changed. **A clock is only half of it: whatever MEASURES the overrun must read the same stored clock.** There are FOUR such measures, not two — `FacilityWorkOrder::daysOverSla()` (it prices a GL penalty), `FacilityWorkOrder::hoursOverSla()` and `::hoursOverResponseSla()` (frozen onto the `sla_penalties` row, quoted in the breach bell and its email, printed on the list) and `TenantRequest::hoursOverSla()` (it words the tenant-request bell) — or the operator is told a three-hour failure is sixty-seven hours old. The first got its branch when the calendar shipped and the last a commit later; the middle two were missed for a week, so ONE penalty row carried an overrun measured two different ways. **Derive a list like this by grep, never from the diff you just wrote** — an invariant enumerated from a diff certifies the coverage you happen to have added. On the working clock a breached figure floors at 1 (a breach that fell entirely across a weekend is not "0 hours late"); on the calendar clock 0 still means "less than an hour", which is a different claim. Ships **off**: the setting is empty until the operator rules on which priorities are office work. **There is no morph map**, so the two rename migrations (`2026_08_15_140000`, `2026_08_15_150000`) backfill 7 polymorphic columns by FQCN; the second one *fails* rather than completes if any row is left pointing at a class that no longer exists, because `LedgerPoster::sync()`'s answer to an unresolvable `journal_entries.source_type` is to void and re-post.
