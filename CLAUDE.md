# Atriom — working guide for AI / dev sessions

Egyptian mall-management ERP · Laravel 13 · PHP 8.4 · Filament 4 · MySQL (prod/local) / sqlite `:memory:` (tests).
Operator **Eltizam** runs malls for owners (**Jawad**); **tenants** are the retailers.

**Read [docs/OVERVIEW.md](docs/OVERVIEW.md) first**, then the relevant **[docs/modules/NN-*.md](docs/modules/)** before changing any module's logic — each has *Business rules*, *Extension points (how to change safely)*, and *Gotchas*.

**Before go-live:** [docs/GO-LIVE.md](docs/GO-LIVE.md) — the single gate: every configuration item, credential and unanswered question, verified against the code (2026-08-11). The code is not the blocker.

**Orientation:** [docs/PROJECT-MAP.md](docs/PROJECT-MAP.md) (generated census — what exists + what's covered) · [docs/ROADMAP.md](docs/ROADMAP.md) (**the single** prioritized list: go-live + FRD + accounting) · the visual handbook — read it **in the panel at `/admin/handbook`** (built by `npm run build`), or as source: [the whole system on one page](docs/visual/map.md), [a month in the life](docs/visual/scenarios.md).

## Conventions — do these
- **Tests:** `vendor/bin/pest --parallel` (Pest 4). Keep it green. Add a regression test for every bug fix in `tests/Feature/Regression/`; scenario tests live in `tests/Feature/Scenarios/`.
- **CI auto-runs are PAUSED** (2026-07-29, owner's call — the pipeline is too slow for the push loop). `.github/workflows/ci.yml` fires only on `workflow_dispatch`. So the conformance gates (PropertyIsolation, GlRegistry, MediaPrivacy, AdminSmokeManifest, **DashboardLayout**, PostingDateGuard, VatRateSetting, **ActionAuthz**, **QueueJobSafety**, **ConcurrencyPolicy**) + PHPStan + Playwright + `composer audit` are **ADVISORY**: nothing blocks a bad change. **Keep `pest --parallel` green locally before every push** — a red push is silent, not a red check.
  - **The jobs themselves were repaired 2026-07-29** and a manual run now actually works: `gh workflow run ci.yml`. All four had been failing on *every* run since ≥2026-07-23 for non-product reasons — `composer audit` missing `--locked` (it audited nothing, ever), PHPStan reading a baseline with **absolute paths** (green on one laptop, red everywhere else), and two timeouts set below the real runtime. Worth a manual run before anything risky.
  - **Cost, measured 2026-08-10: the suite is ~1.5 min** — **795s → 75–97s (~9×)** on the same ~3.68k cases (`pest --parallel`, 10 workers; the spread is background load, so measure on a quiet machine or the numbers lie by 3×). Two independent fixes got it there, and the old note here — ~20 min, blamed on migration replay, with `php artisan schema:dump` as the lever — was **wrong on all three counts**. Migrating 170 migrations into sqlite `:memory:` costs ~1.5s per worker, ~0.3% of the run. The real cost was `RolesPermissionsSeeder`, called from ~230 `beforeEach` blocks (~1,700 test cases) at **925ms a call**: spatie forgets its permission cache on every `saved`, and `Permission::findOrCreate()` reads back through that cache, so building the 182-key catalogue one row at a time reloaded it 182 times. Bulk-inserting the rows and wiring role grants in one pass took it to **11ms** with a byte-identical RBAC end state — verified by diffing both seeders' role→permission dumps (14 roles, 182 permissions, every grant equal), and pinned by `RolesPermissionsSeederBulkWriteTest`. That test warms spatie's cache against an empty catalogue first, because the bulk write's one real hazard is skipping the `saved` hook that would have invalidated it.
  - **The second fix was shape, not speed: Pest parallelises per FILE.** `AllFiltersSweepTest` swept every admin table in ONE 80s case, so it pinned one worker while nine idled and set the floor under the whole suite — no optimisation elsewhere could get below it. It is now sharded across `AdminFilterSweepShard{1..4}Test.php` off shared scaffolding in `Tests\Support\FilterSweep` (a class, not file-scope helpers: a parallel worker only loads the test files it owns, and re-declaring them per shard is a fatal redeclaration). paratest's per-method `--functional` mode would remove the need — but it **crashes** in Pest's `WrapperRunner` (`realpath()` on a `file::method` string), so files are the only unit of parallelism we have. **Sharding costs CPU to buy wall-clock** (each shard re-seeds `DemoSeeder`), which only pays while a file dominates the critical path — past that the binding limit is total CPU ÷ workers, and the answer is to cut work, not split it further.
  - **If the suite slows down again, profile before theorising** — `pest --parallel --log-junit <file>` gives per-case times. Two traps: they are wall-clock under 10-way contention and overstate solo cost by ~5-6× (confirm any suspect file by running it alone), and a run sharing the machine with another suite inflates *everything* ~3.7× uniformly, which reads exactly like a real regression. Known next levers, both measured, neither taken: `DemoSeeder` writes **1,287 activity_log rows** (suppressing them is −21% of its runtime), and it issues **18k queries for 274ms of actual SQL** — the cost is PHP per-query overhead, most visibly ~1,400 repeated `account_mappings` lookups and ~560 `accounting_periods` lookups in the GL posting path, which memoising would speed up in production too.
  - **Suite exits 255 with NO output at all?** That is almost always two test files declaring the same file-scope helper — a fatal redeclaration during collection, before any test runs. It has happened three times (`makeViolation`, `optionOn`, `annualPctLease`). `--parallel` hides it (each worker only loads its own files) and every instinctive recovery — re-run, run the directory, add a `--filter` — loads everything and dies identically. **The one command that works:** `vendor/bin/pest tests/Feature/Scenarios/TestHelperUniquenessConformanceTest.php` — a path-scoped run loads only that path, and the gate names both files. The fix is usually to *reuse* the existing helper, not rename yours; shared ones belong in `tests/Pest.php` or a class under `Tests\Support`.
- **Business logic** goes in single-action services (`app/Services`); keep controllers + Filament pages thin.
- **Docs are part of "done":** changing a module's logic → update its `docs/modules/NN-*.md` (+ `docs/OVERVIEW.md` if cross-cutting) **in the same commit**.
- **Local DB:** MySQL; reseed with `php artisan migrate:fresh --seed` after a feature (`DemoSeeder` = canonical demo data). **`LearningSeeder` is the empty-mall variant** — the same reference data `atriom:install` lays down, one property, 12 vacant units, 3 tenants and *nothing else*, so an experiment's own numbers are the only numbers on screen.
- **Commits:** push to `main` directly (owner's established preference). End commit messages with the `Co-Authored-By:` line.

## Invariants — don't break
- **Money / AR:** `Invoice::recomputeTotals()` is the single source of truth — `paid_amount = captured payments + credit_applied_amount + applied tenant credit (`TenantCreditApplication`) + netted security deposit (`DepositApplication`)`, `balance = total − paid_amount`. Never set `paid_amount`/`balance` directly elsewhere. **FOUR channels, and every calculation that decides "how much of this invoice is settled" must count all four** — adding one means also updating `Invoice::capturedCashPaid()` (none of the three non-payment channels is cash, so the void guard must exclude them), the cancel-invoice release (or the settlement strands on an invoice that left the books), and BOTH payment over-allocation guards (`Payment::assertInvoicesNotOverAllocated()` and `refitAllocationsToBalance()` — omitting one lets a payment over-settle an invoice another channel already paid, burying the excess as negative AR; that has happened once already). **Item-level allocation (`invoice_item_payment`, MF-06) is NOT a fifth channel** — it records how an already-counted settlement splits across the lines. `App\Support\InvoiceItemSettlement` derives every per-line figure from `paid_amount`, so the item outstandings always sum back to `balance`; never store a per-item balance, that is a second truth about the same money.
- **General ledger:** `LedgerPoster::JOURNALIZERS` is the **single registry** of what posts to the GL; all four dispatch paths (real-time hooks · `accounting:sync-ledger` sweep · close gate · `billing:reconcile` drift check) **derive** from it via `LedgerPoster::sources()` — never re-list them. New money source = one registry line + its `LedgerRealtimeSync::SOURCE_DATE_COLUMNS` entry; `GlRegistryConformanceTest` fails CI otherwise. **A GL test that calls `LedgerPoster::post()`/`sync()` directly proves only the journalizer's arithmetic** — at least one test per source must drive the real service + the sweep and assert the tie-out. (This exact gap let applied SLA penalties cut a vendor bill while posting nothing — see [modules/21](docs/modules/21-general-ledger.md#gl-registry-gate).)
- **Tax** on service charges; **base rent is VAT-exempt**. **Marketing levy 5%** of base rent (that one IS a lease term, so it stays in settings — and is now actually editable there: it had no screen at all until 2026-08-12, so "configurable" was a claim only a deploy could honour). Two separate questions, two separate homes: **which supplies are taxable** is `charge_codes.tax_code` — the accountant's ruling, a row, no deploy (where Yardi puts it too) — and **what that tax charges** is the `tax_codes` + `tax_rates` catalogue at `/admin/tax-codes`. A rate is a **dated rung**, never a column: `Vat::rateForType($code, $on)` resolves for the DOCUMENT's date, so a rise can be entered in advance and a back-dated invoice keeps the rate that was in force. `TaxSettings::vat_standard_rate` is GONE (2026-08-12) — settings hold policy, master data holds rates. The catalogue is **the operator's own `account.tax` sheet** ([docs/accounting/EGYPTIAN-TAX-CATALOG.md](docs/accounting/EGYPTIAN-TAX-CATALOG.md)): VAT · stamp · schedule · withholding, each in both directions — **never invent a row beyond it, and never drop one** (`TaxCatalogueConformanceTest` gates both). Stamp + schedule ship SWITCHED OFF because their GL accounts aren't wired; `TaxCode` refuses to activate a taxable code with no rate or no posting role, so an incomplete catalogue is inert rather than a trap. **Every origination point calls `App\Support\Vat::rateForType($code, $on)`** (or `Vat::onType()`); a service calling `standardRate()`/`on()` directly can't see the ruling and fails `ExemptChargeTypesAgreeAcrossPathsTest`, and a literal rate anywhere fails `VatRateSettingTest`. `Vat::EXEMPT_TYPES` + `Vat::DEFAULT_STANDARD_RATE` are the FLOOR for an unseeded catalogue, not the policy — they must resolve identically to the seeded catalogue (`ChargeCodeVatTreatmentConformanceTest`), exactly as `InvoiceJournalizer::REVENUE_ROLE` floors the posting roles. Only **origination** reads any of it: an issued invoice keeps the rate it was billed at, so neither a rate change nor a treatment change ever rewrites history. **For a recurring charge, origination is BILLING, not the day the schedule row was written** — `charges.vat_rate` is an OVERRIDE and null is the normal state, with `Charge::resolvedVatRate($on)` the one place that answers what it bills on a date. Storing the catalogue's answer on the row is what broke this until 2026-08-12: the rate froze for the life of the lease, so a rise entered in advance reached every one-off charge and **never reached rent or service charge** — most of the money — and the amendment path carried the stale rate onto the new row too. Proven, not argued: with a rise to 20% effective 1 Sept, the resolver answered 20 for a September document while the September invoice billed 14. `vat_applicable = false` still wins over both, and after the backfill it is the ONLY thing holding an untaxed row (`VatRiseReachesRecurringRentTest`). **A document line records WHICH tax it carried** (`invoice_items.tax_code`, defaulted at the MODEL layer from the charge code so the eight line-raising services can't forget it) — a classification beside the rate, never a pointer the totals re-derive through. **The rate is picked, not typed**: read-only without `tax_codes.override` (withheld from `manager` — departing from the catalogue is an accounting act), enforced server-side by `App\Support\CatalogueTaxRate` from the items repeater's `mutateRelationshipData…Using` hooks. **That layer is load-bearing** — the repeater is relationship-backed, so rows never reach the page's `mutateFormDataBeforeCreate` and a guard written there protects nothing.
- **Money records are NEVER deletable — not even by super_admin** (operator decision 2026-07-31). Invoice, Payment, JournalEntry, CreditNote, VendorBill, Expense, DepositTransaction, Payroll, PostDatedCheque: no Delete/ForceDelete action, no `{module}.delete` permission, and a model-level refusal (`RefusesDeletionOfCommittedRecords`) as the backstop. Correct them through their own workflow — cancel / void / credit note / reverse — which leaves a document an auditor can follow. An UNCOMMITTED record is still removable (a draft journal entry, a payment that never became money), which is what keeps `CreatePayment`'s orphan rollback working. Registry = `App\Support\DeletionPolicy`; `DeletionPolicyConformanceTest` fails the build if a Delete button or permission reappears. **Master data with history is refused too** (`DeletionPolicy::WHEN_UNUSED` — Tenant, Vendor, Lease, Unit, Asset, Employee): deletable only while nothing references it, otherwise deactivate. This follows Yardi/MRI/Entrata, which all refuse rather than warn — the damage lands on the reports and audit trail that referenced the record, not on the record itself. `blocked_by` relations are verified to EXIST by the gate (a typo'd relation blocks nothing and looks identical to a working guard). Note `Unit` uses `allLeases` (the pivot), not `leases`. **Every model is classified** — `NEVER_DELETABLE` / `WHEN_UNUSED` / `ALLOWED` (with a stated reason) — and the gate fails on an unclassified one, so a new model forces a decision rather than inheriting a default. Before adding anything to `NEVER`, check for a real deletion call site in `app/`: guarding a row a service legitimately deletes breaks the workflow instead of protecting it (that check saved the credit-note un-apply, the tenant-credit reversal, the owner-statement rebuild, and the advance-repayment reversal). Two models are deliberately `ALLOWED` despite carrying history — `UtilityMeter` and `FixedAsset` — because soft-delete IS their tested retirement path and the GL/trend already handle it; both omissions are annotated in the registry. **Everything else: delete = super_admin only**; bulk-delete is off project-wide (opt-in via `$bulkDeletable`). CRUD gating via `RoleGatedActions` on `{module}.{action}` permissions (`RolesPermissionsSeeder`).
- **Property isolation:** every module is isolated to the selected property. **Reads:** resource tables auto-scope; scope any cross-property Filament select via `App\Support\TenantScope::selectable*` / `visibleAssetIds()` (never `currentAssetId()` alone — null in All-mode leaks); "All Properties" pseudo-asset = `Asset::ALL_PROPERTIES_CODE`. **Writes:** if a form exposes/derives an editable `asset_id`, guard it with `GuardsAssetInScope::assertAssetInScope()` on create+edit (Filament only stamps `asset_id` on create, never update). Shared-vs-isolated register = `App\Support\PropertyIsolation`; the `PropertyIsolationConformanceTest` gate fails CI if a new model/resource ships unclassified/unscoped/unguarded. **Read [docs/PROPERTY-ISOLATION.md](docs/PROPERTY-ISOLATION.md) before adding a property-owned module.**
- **Auth surfaces:** `/admin` = `User` + spatie roles · `/portal` = `TenantUser` (multi-user; only `is_admin` may write) · `/api/v1` = Sanctum `tenant-api` against `Tenant`. Cross-tenant API returns **404** (no existence enumeration).
- **`visible()` is NOT an authorization gate.** (`ActionAuthzConformanceTest` now gates this: every `Action::make()` chain under `app/Filament` carrying an `->action()` must also carry `->authorize()`/`abort_unless`, or be registered in `App\Support\ActionAuthz::EXEMPT` with a reason.) **Correction 2026-07-31 — the "still dispatchable" half of this was WRONG on the version we ship.** `mountAction()` does check `isDisabled()`, and `CanBeDisabled::isDisabled()` returns true when `isHidden()` does (`vendor/filament/actions/src/Concerns/CanBeDisabled.php:24`), so on **Filament v4.11.8 a `visible()`-only action IS refused at dispatch**. Found by mutation-testing the module-08 fix: deleting CAM's `abort_unless` left `CamActionAuthzTest` fully green — those tests never exercised the gate they describe. **The second layer is now real, and global (2026-08-12).** `Action::make()` resolves through the container, so `Filament\Actions\Action` is bound to `App\Support\Filament\AuthorizedAction`, which runs `abort_unless($this->isAuthorized(), 403)` inside `call()` — the check Filament's own `Action::call()` never performed. That closes FS-23 at one seam instead of in 76 files: `->authorize()` folds into `isHidden()` folds into `isDisabled()`, so on the letter of it `visible()` and `->authorize()` were one layer, and the 76 write actions gating with `->authorize()` alone (journal-entry post/void, void_invoice, period close) had no second one. `isAuthorized()` returns true when nothing was declared, so the ~500 actions gating with `abort_unless` are untouched. `ActionCallIsAuthorizedTest` pins the refusal AND the binding, so a Filament release switching `make()` to `new static` turns the build red rather than quietly removing the layer. **Double-gate anyway**, for a reason that survives the correction: `->authorize()` is a stated intent, while hidden-implies-disabled is an upstream implementation detail that can change in a release and would silently reopen every `visible()`-only write at once. `FilamentActionDispatchContractTest` pins that upstream behaviour so an upgrade that changes it turns the build red; `ActionAuthzConformanceTest` enforces the layer we control. Every write action must gate in **both** `visible()` (the UI) and `action()` (`abort_unless(...)` — the actual gate); name the predicate once so they can't drift. **In tests, neither `->callAction()` NOR `mountAction` proves the `action()` gate** — `callAction()` asserts visibility first, and `mountAction` refuses hidden actions for the reason above, so both go green whether or not the gate exists. To prove a gate, remove it and watch the test fail; to test one, assert the predicate directly. And always pair a refusal test with an authorised control — a refusal passes just as happily when the dispatch is a no-op.
- **Search:** every searchable model carries a fold-normalized `search_text` blob (`App\Models\Concerns\HasSearchText`), and BOTH sides go through `App\Support\Search\SearchText` — the stored value and the operator's query. Folding one side matches nothing. Resources search `['search_text', 'tenant.search_text', …]` and **never a raw column**: a path pointed at `tenant.name` compares a folded query against an unfolded value, so it silently misses exactly the Arabic spellings the fold exists to fix («شركة»/«شركه», «أحمد»/«احمد») while still working for plain ASCII — which is what anyone spot-checking it would try. **The blob is a pure function of the row's OWN attributes** — never reach through a relation, or renaming a tenant strands every invoice blob that quoted it. Two hooks, not one: `saving` is too early for document numbers (`AllocatesDocumentNumber` assigns `number` in `creating`, so a saving-only fold stores a blob with no invoice number) and for id-derived accessors (`Violation::$reference`), so `created` re-folds when the value changed. Registry = `App\Support\SearchPolicy` (indexed models · exemptions with reasons · category order · query floor); `SearchPolicyConformanceTest` fails the build on an unclassified resource, a raw-column search key, a relation path whose model has no blob, or a table rendering a search box it could never answer. Adding a model to `INDEXED` needs its own migration — the existing one is a fixed snapshot. **Changing the fold or a `searchTextSources()` rewrites nothing on its own — run `php artisan atriom:rebuild-search`.** Search inherits authz + property isolation via `getEloquentQuery()`; don't re-implement either in the provider. *(Testing trap: Filament drops any result whose URL is blank, which is derived from `canView()`/`canEdit()` — so a search test that doesn't seed `RolesPermissionsSeeder` returns zero for everything and every refusal assertion passes for the wrong reason. Always pair a refusal with a control that must find something.)* See [docs/modules/34-search.md](docs/modules/34-search.md).
- **Activity log — it stores DATA, never PROSE.** A row records `log_name` · `event` · field keys · raw values; every human-readable word is resolved at READ time by `App\Support\ActivityVocabulary`. That is what lets one stored row read correctly in Arabic and English, and what lets a wording fix reach rows written years ago — a sentence baked in at write time (`->log('Invoice voided')`) can never be either, so **a description is a KEY** (`invoice.voided`, nested under `admin.activity.descriptions` because `__()` reads dots as nesting). **Always pass a log name** — bare `activity()` files under spatie's `default`, renders as "Other", and is invisible to the log-name filter. Field labels reuse **`admin.fields.*`, the catalogue the FORMS label from** (same word for the same field); enum-ish values resolve via `admin.statuses.{log_name}` by convention or a `VALUE_VOCABULARY` entry pointed at **the group the form's `Select` reads from** (picking a group because its keys overlap gave `expense.category` the RETAIL list); `*_id` columns resolve through `FOREIGN_KEYS` so a diff names the record instead of printing an id, which needs the model to be nameable (`label()`/`displayName()`, else `reference`/`number`/`name`/`code`/`title`). `ActivityVocabulary` is a **singleton** — `preloadReferences()` batches a page to one query per table and every cell reads that cache, so a transient binding silently restores the N+1 while looking identical. **`Lang::has($key, 'ar')` FALLS BACK to English** (`has($key, $locale, $fallback = true)`), so an EN↔AR parity check written the obvious way only ever catches keys missing from BOTH — every parity check passes `fallback: false`. `ActivityLogVocabularyConformanceTest` gates all of it, and asserts its own sweeps found something first (its predecessor filtered on a trait FQCN that doesn't exist in the version we ship and was green for a year while sweeping zero models). **Adding a model or a hand-written `activity()` call → follow [modules/18 → Extension points](docs/modules/18-rbac-scoping.md).**
- **Uploaded files:** every media collection must declare its disk explicitly — `useDisk('local')` (private) unless it is branding. medialibrary's default is `env('MEDIA_DISK', 'public')`, i.e. **fail-open**: forgetting to register a collection silently publishes it to the webroot (this exposed signed leases + tenant tax cards). `MediaPrivacyConformanceTest` gates it.
- **NOT-NULL columns:** never let an optional/blank form field send `null` into a NOT-NULL column — coerce in the model (this class of bug bit us: `meter_readings.cost`, `leases.has_percentage_rent`).
- **No DB-level enums — the count is ZERO and the gate keeps it there.** Never `$table->enum(...)`; use `string(32)` and add the value set to `App\Support\ValueSets`, which `AppServiceProvider`'s wildcard `eloquent.saving: *` listener refuses out-of-set values against on every model save. One seam, not a trait on 39 models, for the reason that put `AuthorizedAction` in the container: the fortieth model is covered before anyone remembers it. All 62 remaining enum columns were converted 2026-08-12 (`2026_08_12_270000_free_every_remaining_db_enum_column`); widening a set is now a one-line code change instead of an `ALTER TABLE … MODIFY` on `payments`, which is what stopped the operator adding a payment rail without a deploy in a market where the rails keep moving. **Don't re-list a set** — importers and forms read `ValueSets::allowed()` (`Rule::in(...)`); a deliberately NARROWER rule is fine but must say so, as `UnitImporter`/`LeaseImporter` do. **Two drivers express this differently and only one is in your test run:** MySQL has an enum TYPE, SQLite renders `enum()` as `varchar check (…)` and then **silently drops that check on any `->change()` to the table**, because it rebuilds from the introspected schema. That is not theory — it is how 24 columns came to be enums in production and unconstrained in tests, while a gate reading the test schema passed. `NoDatabaseEnumsConformanceTest` reads BOTH shapes and proves the listener refuses; a value the model allows but the column rejects is otherwise green here and fatal on the first real save.
- **Changing a posted document:** the ledger here is **derived, not journalled** — `LedgerPoster::sync()` re-reads a document and, when its posted entry no longer matches, **voids it and posts a fresh one**. So "may this edit move the books?" is a decision, and every fillable column of every GL source declares it in `App\Support\ChangeImpact::POLICY`: **REFUSED** (immutable once committed — correct via a new document) · **DERIVED** (entry is void-and-reposted) · **PROSPECTIVE** (future documents only) · **DESCRIPTIVE** (reaches the entry's description but never re-derives, because `matches()` compares lines + date + asset and not text) · **NEUTRAL**. The governing rule: **a change may re-derive a posted entry only while that entry is not yet evidence** — filed with ETA, delivered to the counterparty, inside a closed period, or inside an issued owner statement. `ChangeImpactConformanceTest` fails the build on an unclassified field, on a classified column that no longer exists, on a field a journalizer reads being called neutral, on a posting-date column classified neutral — and **proves every REFUSED field by dirtying it on a committed fixture** rather than asserting a guard exists. A source declaring refusals must add that fixture. See [docs/accounting/CHANGE-IMPACT-PLAN.md](docs/accounting/CHANGE-IMPACT-PLAN.md).
- **Posting dates:** any date that becomes a journal entry's `entry_date` must be refused when its period is **closed** — otherwise the row commits, the operator sees "Saved ✓", and the entry is refused inside the best-effort sync job that only logs. Every GL source declares its guard in `App\Support\PostingDateGuards::GUARDS` (a guard class, or a `system:` reason why the date can't be operator-typed); `PostingDateGuardConformanceTest` fails if a new source ships unclassified. Guard in the **service**; use the `GuardsPostingDate` model trait only where there is no create/update service. A **MISSING** period is allowed — only a CLOSED one is refused. *(This exact bug was fixed six times, one module at a time, before the gate existed.)*
- **A `DomainException` is a refusal, not a fault** — it renders as a message + redirect-back (`bootstrap/app.php`), never the 500 page. Throw it for anything the operator did that isn't allowed. **The redirect is followed by Livewire's own `fetch`**, and a same-origin redirect keeps the headers — so the page it lands on is fetched still carrying `X-Livewire`, which is the *whole* of Livewire's `isLivewireRequest()`. Filament then reads that page GET as a component update, asks `PersistentMiddleware::makeFakeRequest()` for a request that doesn't exist, and the page **405s**. `IgnoreStrayLivewireHeader` (global, prepended) strips the header off safe-method app routes so the refusal renders as its toast. Until 2026-07-31 every Livewire-raised refusal in both panels showed a "Method Not Allowed" modal instead of its reason — `DomainRefusalIsNotAnErrorPageTest` was green throughout because it asserted the 302 and never followed it; `RefusalRedirectSurvivesLivewireHeaderTest` follows it.
- **Scheduled scans** must be idempotent + lock-safe (`lockForUpdate` + re-check the stamp inside the transaction).
- **Concurrency: every lock is registered, and the registry has teeth.** `SQLiteGrammar::compileLock()` returns `''` and the suite runs on sqlite `:memory:`, so **all 118 lock acquisitions are inert in every test** — deleting one used to turn nothing red, in the one invariant class this project has actually been bitten by twice (the unit double-booking, the Paymob double-charge). `App\Support\ConcurrencyPolicy` registers every file that takes a row lock (`lockForUpdate`/`sharedLock`) **or an atomic cache lock** (`Cache::lock` — same guard, different mechanism, used where the thing protected is a sequence rather than a row), **with its lock count**; `ConcurrencyPolicyConformanceTest` fails on an unregistered file, on a registered file that stops locking, and on count drift — so one lock dropped from `CreditNoteService`'s eleven is visible. The `PROVEN` tier goes further: `Tests\Support\LockSpy` swaps in a grammar that compiles the lock to a **SQL comment** (valid SQLite, behaviour-neutral), so `DB::listen()` can see which table a service actually locked on the real path — those tests fail when the lock is removed. **A lock on the right table is not proof the service under test took it**: with auto-apply-credit on, the late-fee test passed with its own lock deleted because another service locked `invoices` in the same request. Isolate, then mutate. None of this proves two transactions serialise — that needs MySQL and two connections, and is stated as out of scope rather than implied.
- **Every screen explains itself, in both languages.** `App\Support\ScreenGuides::SCREENS` maps all **83 screens** (49 admin resources · 27 admin pages · 7 portal resources) to a four-field guide in `lang/{en,ar}/guides.php` — *purpose · steps · affects · rules*. `affects` is the field that earns the panel: what moves ELSEWHERE when you touch this screen is the one thing nothing else in the app tells anyone. The panel mounts as `GuideAction::for(static::getResource())` on a resource's List page and `GuideAction::for(static::class)` on a page. `ScreenGuideConformanceTest` discovers every screen class on disk and fails on one that is neither registered nor `EXEMPT` with a reason — **and separately checks it is MOUNTED**, because a written guide nobody can open helps nobody. `EXEMPT` is empty and the gate rejects a stale entry: the login and tenancy-registration screens extend `SimplePage`, not `Page`, so discovery never offers them. The portal has its own `portal_*` namespace — a guide telling a tenant what the billing run does answers a question they cannot act on.
- **Field help is sorted by what it DOES, not stacked under the field.** Three homes: `helperText` (always visible) carries only what changes what you type — a constraint, a derivation, a consequence, or live feedback computed at runtime; `->hintIcon(Heroicon::OutlinedQuestionMarkCircle, __('admin.hints.X'))` carries the WHY, one hover away with a visible affordance; the screen guide carries what is really about the module. Budget is **18 words** (`App\Support\FieldHelp::WORD_BUDGET`) — twelve turned good one-liners into fragments. `FieldHelpConformanceTest` gates the budget (exemptions carry a reason in `LONG_BY_DESIGN`), a hint icon with no tooltip, a hint written-but-never-shown OR shown-but-never-written, and an exemption whose string is already short. **Tooltips are not a substitute for a visible constraint** — hover vanishes on touch, and a first-time operator cannot see the rule that would have stopped them. Check the CALL SITE before shortening: a string already rendered as a `->tooltip()` or `->modalDescription()` is already one hover away, and one reporting record STATE is live feedback, not explanation.
- **The visual handbook is IN THE PANEL, bilingual and partly generated.** Read it at `/admin/handbook` (a Filament page) or directly at `/handbook`. The panel page **frames** the built site rather than rendering it inline, and that is the right call rather than a compromise: the handbook runs a Vue app and the panel runs Livewire + Alpine, so inlining would put two SPA runtimes in one document and the interactive components would break first. Same-origin, so the parent drives the child directly — no postMessage protocol. The frame takes the panel's light/dark and its per-property `--primary-*`, drops its own nav via `?embed=1` (asked for, never sniffed from `window.top` — a second window wants the full site), and follows the reader's language. **`npm run build` builds it**: it chains `docs:build`, which regenerates the datasets and renders the site, so the handbook can never be a release behind the code. Output goes to `storage/app/handbook` — **outside the webroot on purpose**, so nginx cannot serve it and the `auth` on `/handbook` genuinely applies; missing, it answers **503 naming the missing step**. EN at `/`, AR at `/ar/`, **26 pages per locale at parity**. RTL works with **no plugin** because `theme/custom.css` uses CSS logical properties — a single `left`/`right` would force `postcss-rtlcss` back in. `atriom:dump-handbook-data` writes five datasets from the registries; `HandbookDataConformanceTest` fails on drift and pins that **no money record ever dumps as deletable**. **Never hand-type a count or list a registry already holds** — five statements in that handbook had gone stale (settlement channels, the journalizer count twice, the module count, a removed panel) and all five surfaced only when someone translated them. The Dr/Cr lines per journalizer are deliberately NOT generated: they resolve through `ChargeCode::roleFor()` at runtime, so any map would be a guess drawn as a diagram.
- **Terminal records** are immutable: closed/cancelled maintenance, responded owner-requests.

See the naming note below.)*

**"Maintenance" is not an identifier in this system (2026-08-15).** The word meant five different things and only two of them were ever the same module, so it is now reserved for the four places it is plain English rather than a name:
- `units.status = 'maintenance'` — a unit out of service ("Under Maintenance")
- the `maintenance` expense / vendor-bill category — posts to `maintenance_expense`
- `TenantRequestType::Maintenance` — a maintenance request is one KIND of tenant request
- Laravel's own maintenance mode (`php artisan down`)

Everything else moved. Module 11 (tenant requests) → `requests.*` permissions, `Modules::enabled('requests')`, `config/requests.php`. Module 26 (facility) → `facility.*` permissions, `Modules::enabled('facility')`, models `FacilityWorkOrder` / `FacilityWorkOrderItem` / `FacilityWorkOrderPart` / `ServicePlan` / `SlaPenalty` over `facility_work_orders` / `service_plans` / `sla_penalties`. The SLA hours both modules read are `SlaSettings` (group `sla`) + `config/sla.php` — named for neither module on purpose, because naming shared settings after one consumer is what created the confusion in the first place. **There is no morph map**, so the two rename migrations (`2026_08_15_140000`, `2026_08_15_150000`) backfill 7 polymorphic columns by FQCN; the second one *fails* rather than completes if any row is left pointing at a class that no longer exists, because `LedgerPoster::sync()`'s answer to an unresolvable `journal_entries.source_type` is to void and re-post.
